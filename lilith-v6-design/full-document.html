Architecture decisions already locked

  • ✓ Frontend framework: PySide6 6.11.1 (LGPL v3) + ModernGL 5.x (MIT) for the orb via QOpenGLWidget. Qt Quick 3D dropped (GPLv3-only, incompatible with closed-source distribution).
  • ✓ Voice is the default, non-negotiable at the Tier 0 minimum: STT (Whisper) + TTS (Kokoro) run on every supported machine. The desktop chat screen also accepts typed input at any time, with TTS available on demand per message rather than forced — see §13, §22.
  • ✓ All databases: SQLCipher from first migration. No plaintext SQLite anywhere.
  • ✓ All credentials: OS keychain via python-keyring. Never in .env, never in config files.
  • ✓ External APIs (v6 v1): Read-only. Lilith manages her own calendar and contact roster separately.
  • ✓ Two-mode router architecture: Conversational vs Artifact (acknowledge → background → handoff). The two-mode split itself is locked; its tuning numbers (≤50 output tokens, ≤3 s to audio, ≤1200 context tokens) are v6 v1 working hypotheses to be validated in Milestone 1, not immutable constants — see §13.
  • ✓ LLM access: L1/L2 enhanced data only. Raw DB rows never enter the context window.
  • ✓ BYOK: User-provided API keys. No managed cloud inference from Lilith.
  • ✓ Path handling: pathlib.Path everywhere. No string path concatenation, no hardcoded separators.
  • ✓ Distribution model: Lilith v6 is free, closed-source, no license key, no activation. Wide distribution is the goal. Revenue comes from a future cloud sync subscription (Obsidian model). v6 v1 has no paid features — users bring their own API keys and their own Google account. No piracy surface to protect against.
  • ✓ Memory recall (v6 v1): Recency-first + FTS5 keyword search. No local embeddings or vector search in v6 v1 — that is a future phase. See §18 for full spec.
  • ✓ Custodian Model: All internal data (SQLCipher databases, salts, config, logs, cache, models, and skills) lives in a single OS-standard application directory (APP_INTERNAL_DIR) with strict POSIX 0700/0600 permissions. The user's primary files, notes, and documents (including external Obsidian note vaults) are never copied to Lilith's storage; she acts as a custodian, maintaining paths/pointers and indexing summaries. Accumulated history (UCL, memory, conversation DBs) is portable via Lilith's backup/restore utility. See §04, §29.

01Project Structure & ConventionsComplete▶

Standardized on a clean multi-layered Python 3.12 architecture with a strictly enforced downwards-only dependency flow and cross-platform pathlib.Path handling.

  • Python Version: Python 3.12 (enforced via .python-version and pyproject.toml) for stability and wheel compatibility with core binary libraries (e.g., ctranslate2, sqlcipher3-wheels).
  • Package Management: pip + requirements.txt (generated from pyproject.toml) for reproducible, deterministic dependency resolution.
  • Path Handling: Strict pathlib.Path usage for all I/O, database paths, and platform calls (no string concatenation, no hardcoded separators; enforced via lint checks).
  • Module Boundaries: ui → logic → data → platform. Circular imports are blocked and verified using import-linter in CI.
  • Naming Conventions: snake_case for files, PascalCase for classes, UPPER_SNAKE for constants, snake_case for database tables, and dot.namespaced (e.g., voice.stt.complete) for event types.
  • Configuration Management: Stored in config.json located in the OS-appropriate app directory. Schema migrations for config options are handled programmatically on startup.
  • Error Handling: Recoverable errors are caught at module boundaries, passed through the telemetry sanitizer, logged to the UCL database with redacted messages only, and surfaced to the user. Unrecoverable failures (missing keychain, corrupted database) display a dedicated recovery screen or hard exit.
  • Logging: Stdout/stderr reserved for dev/startup. UCL database logs all user and system behavioral telemetry. Exception logging must go through the same sanitizer before any write, including dev logs, startup logs, UCL payloads, and recovery telemetry.
  • Git Workflow: feature/* or bugfix/* branch naming, mandatory PRs, and commit messages prefixed with [scope]:.
  • Done-Criteria Standard: log_event() on all success paths, security audits for raw data, UCL payload schema review for every new event, 80%+ test coverage (excluding hardware/audio I/O), and a wiki page updated.

02Security & Credential ManagementComplete▶

Credentials are managed through the OS keychain using python-keyring in convenience mode, or entered at launch in prompt mode, with strict startup safety checks that disable insecure fallbacks and a separate file for database salts to enable robust offline restores.

  • Keychain Service Name: "com.squirrelthug.lilith" (the unique namespace string used for all OS keyring queries).
  • OS-Specific Keyring Backends:
    • Linux Desktop: SecretServiceKeyring (Freedesktop Secret Service API via D-Bus).
    • macOS: macOS Keychain (Generic Password item class, secGenericPassword).
    • Windows: WinVaultKeyring (Windows Credential Manager encrypted via DPAPI).
  • Keychain Security Verification: Startup checks verify that keyring.get_keyring() returns a secure backend. If an insecure plaintext fallback (like keyrings.alt) or a failed keyring (FailKeyring) is detected, the app refuses to boot and raises an unrecoverable security exception.
  • Stored Credentials List & Key Names (Canonical Table):

    All secrets are managed under the unified service namespace "com.squirrelthug.lilith". In-memory access tokens are never persisted.

  • Salt File: Stored at APP_INTERNAL_DIR/databases/salts.dat. Format is exactly 192 bytes binary, consisting of six contiguous 32-byte cryptographically secure random salts (one for each of the 6 databases: ucl_db, calendar_db, contacts_db, finance_db, memory_db, conversation_db in fixed index order). Loaded via pathlib.Path.read_bytes(). It has exactly three legitimate origins (SEC-025): it is generated via os.urandom(192) inside onboarding's clean-install path (§25 Step 5) and only when no database files exist — never eagerly during startup classification (§06 Phase 4), where premature generation would mask the §25 reinstall-detected state; it arrives as part of a restored backup set (§25 restore-from-backup flow); or it is regenerated by the passphrase-change flow (the Stage step of the Passphrase Change & Key Rotation flow below / §03 Key Rotation Mechanics), where fresh salts are staged and swapped only as part of the §06 rotation journal's committed batch. The "only when no database files exist" rule scopes to startup/onboarding classification — it exists to protect the reinstall-detected state and does not forbid rotation's staged salt regeneration, which never generates salts outside a committed rotation batch. If databases exist but the salt file is missing, startup halts with a recovery error.
  • Security Tier Setting (v6 v1): Lilith ships two unlock modes. Convenience mode is the default and stores master_passphrase in the OS keychain so startup can auto-unlock. Prompt mode is available during onboarding and in settings; it never persists master_passphrase in the keychain, requires the user to type the passphrase at each app launch, and keeps derived database keys in process memory only until explicit relock or app exit. Switching from convenience mode to prompt mode deletes the persisted master_passphrase keychain item after verifying the typed passphrase can open all six databases. The keychain may still contain non-secret state such as install_sentinel and security_tier; these values do not unlock data. Recorded decision — default tier (2026-07-12, accepted risk): Convenience mode remains the default on all three platforms, including Linux, where the Secret Service caveat in the threat model below means any same-user process can read master_passphrase over D-Bus. Hands-free voice startup is the product's identity, and the threat model already concedes the same-user adversary. A platform-aware default (prompt mode as the Linux default) was considered and declined for v6 v1. This acceptance is conditional on §25's tier-selection step displaying the static Linux keyring-exposure warning and presenting both tiers with equal discoverability (AC-OB-004 through AC-OB-007); revisit this decision if dogfooding or user reports show the warning is insufficient.
  • Keyring Failure Recovery: If the keyring is unavailable or returns errors on startup, Lilith halts and displays a clear error screen: "OS secure keychain is unavailable. Please verify your system's keyring daemon is running."
  • Data Hygiene (SEC-018, Normative): Raw database rows never leave the device. Before cloud dispatch, the §14 tokenizer replaces person names, email addresses, and phone numbers in the compiled context with anonymous tags on a best-effort basis (rule-based detection; recall is not guaranteed, particularly for unusual names, nicknames, possessives, and names inside quoted message text). All other L2/context content — including merchant names and monetary amounts, health and relationship details, free-text notes, and location text outside §19's deterministic calendar-address preprocessing — is not detected and is sent as-is to the user's own BYOK provider over TLS, and never to any Lilith-operated service. Privacy-copy ceiling rule (Normative): any onboarding, marketing, or privacy copy describing this behavior must be derived from this paragraph as amended — the design document is the ceiling for user-facing privacy claims, never the floor; copy may claim less than this paragraph states, never more. No keyring operations are logged to prevent timing/leak vulnerabilities.
  • Directory & File Permissions (POSIX/Windows): All directories in APP_INTERNAL_DIR are created with strict 0700 permissions (directories) and 0600 (files) on POSIX. On Windows, per-user profile ACLs are set via DPAPI and NTFS permissions. Startup checks verify and enforce these permissions.
  • Threat Model & Security Boundary: SQLCipher encryption at rest protects user data from offline/at-rest attackers (e.g., physical media theft, disk exfiltration, backup leakage, or copied database files without the passphrase). It does not protect against a compromised active user session, same-user local malware, debugger access, process memory compromise, or a malicious process that can drive the unlocked app. On Linux, the Freedesktop Secret Service API has no per-application ACL, so any process in the same user session may be able to request keychain items over D-Bus; macOS and Windows provide stronger app/user binding but same-user malware remains outside the encryption-at-rest boundary. Convenience mode therefore protects powered-off/stolen/copy-only scenarios, not an already-compromised login session. Prompt mode reduces persistent keychain exposure but still cannot protect data once the passphrase has been entered and Lilith is unlocked.
  • Passphrase Change & Key Rotation (SEC-009, Normative): The master passphrase is changed only through the guarded passphrase-change flow, a rare foreground operation available in Settings in both security tiers. It runs with a progress UI and may take minutes; data safety strictly dominates speed. The flow is, in order:
    1. Verify: The user types the current passphrase — required in both tiers; the keychain value is never accepted as proof of user intent. Keys are derived per §03 and verified against all six databases before anything else happens.
    2. Collect: The user types the new passphrase twice, subject to the same minimum-length, confirmation-match, and strength/blocklist rules as onboarding Step 3 (§25).
    3. Preflight: Free disk space of at least the combined size of all six databases plus a 20% margin is confirmed; scheduled jobs (including the §06 daily backup) are paused; a fresh integrity-checked backup set is taken under the current passphrase as the guaranteed restore point.
    4. Stage: Six new 32-byte salts are generated — salts are always regenerated on rotation — new per-database keys are derived per §03, and each database is exported via sqlcipher_export() into a staged copy under the new key and integrity-checked (see §03 Key Rotation Mechanics). The live files are untouched during staging.
    5. Commit: All database connections are closed and the staged databases plus the staged salts.dat replace the live files as one committed batch under the crash-resumable rotation journal defined in §06.
    6. Finalize: Databases are reopened and verified under the new keys through a freshly constructed SessionKeyManager; only then — and in convenience mode only — is the keychain master_passphrase entry updated. The keychain write is always the final step of a completed database re-key; there is no code path that updates the keychain entry without a completed re-key. A fresh post-rotation backup is then taken immediately.
    Every step emits security.rekey.* UCL events (§06 lists the event set, §16 defines the namespace) whose payloads carry phase, database name, and durations only — never passphrases, salts, key material, or PRAGMA text (§03's keying exception boundary and §16's sanitizer gate apply). If the flow is interrupted at any point, the §06 rotation journal guarantees deterministic rollback or roll-forward at next startup.
  • Master Passphrase Write Path (Normative): Settings has no direct write control over master_passphrase. The only writers of that keychain entry are onboarding (§25 Step 3/4) and the final step of the passphrase-change flow above. Implementations must not provide any settings field, API, or code path that updates the keychain master_passphrase entry independently of a completed database re-key — a keychain-only passphrase change guarantees lockout (keychain holds the new passphrase while the databases remain keyed under the old one).
  • Credential Update & Revocation (Settings): All non-master secrets in the canonical table (anthropic_api_key, openai_api_key, ollama_bearer_token, google_oauth_refresh_token) are plain keychain values with no database-key coupling. Settings updates them by direct overwrite (keyring.set_password, taking effect on next use) and revokes them by deletion (keyring.delete_password plus invalidation of any in-memory client holding the old value; Google revocation additionally calls the provider's token-revocation endpoint on a best-effort basis). These simple keychain writes are explicitly distinct from the master-passphrase path above, which is never a simple keychain write. Non-secret entries (install_sentinel, security_tier) follow their existing §25/§02 writers.
  • Explicit Re-Lock (Normative): "Relock" means: all database connections are closed (WAL flushed), the SessionKeyManager and every derived key are dropped from process memory via SessionKeyManager.relock() (§03), scheduler jobs requiring database access are paused, voice capture stops, and the UI returns to a locked screen. A manual "Lock Lilith" action in Settings and the tray menu triggers relock in both tiers; relock and the subsequent unlock emit security.relock / security.unlock UCL events. Resuming from the locked screen: prompt mode requires the typed passphrase; convenience mode offers one-click unlock via the keychain (manual relock in convenience mode guards against casual physical access, not same-user malware — see Threat Model above). Recorded decision — idle-timeout auto-relock (2026-07-12): deferred beyond v6 v1. Lilith is a voice-first, always-listening assistant with scheduled background jobs (e.g. the 03:20 backup); an idle auto-relock would silently break wake-word response and scheduled work. It is recorded as a future opt-in for prompt mode, not a v1 requirement.
  • What Rotation Does — and Does Not — Do: Rotating the passphrase re-keys the live store, protects all future backups, and revokes the forward usefulness of a leaked keychain value or captured passphrase. It does not re-protect data already exfiltrated: any backup set (databases + salts) copied off the device under the old passphrase remains decryptable with that old passphrase forever. After a suspected compromise, rotation limits future exposure; it cannot recall the past. The flow takes a fresh backup automatically at finalize; retained older sets are not re-keyed and age out under §06's 7-set retention policy (see §06 Backups Across Rotation).

03Encryption at Rest — SQLCipherComplete▶

All six databases are encrypted with AES-256 using the sqlcipher3-wheels package, bypass connection latency via raw hex keys derived by Argon2id, and manage concurrent thread access using WAL mode.

  • Python Package: sqlcipher3-wheels (AES-256 database engine). Pre-compiled binaries are utilized to ensure cross-platform installation success without local build dependencies, with fallback build instructions logged.
  • Database Inventory:
    • ucl_db: Telemetry and Universal Communication Log event rows.
    • calendar_db: Google Calendar read-caches and local calendar events.
    • contacts_db: Google Contacts read-caches and local people roster.
    • finance_db: Accounts, transactions, and category YAML paths.
    • memory_db: Memory entries, FTS5 keyword index, and personal truths; a model-versioned embeddings sidecar table is reserved by the §18 Recall Roadmap (not in v6 v1).
    • conversation_db: Chat sessions, message turns, and token metrics.
  • Key Derivation Pipeline: 
    Master Passphrase (User Input/Keychain) + Salt (salts.dat Index)
  ↓
Argon2id (time_cost=3, memory_cost=65536 KiB, parallelism=2)
  ↓
32-byte Binary Output → SessionKeyManager-owned Hex String (64 chars)
  ↓
PRAGMA key = "x'<64 hex chars>'" (Bypasses SQLCipher internal PBKDF2)
  • Key Manager Object: Database keys are derived once per unlocked session and held by a single SessionKeyManager object. Callers request database-specific keying through that object instead of passing loose hex strings between functions. SessionKeyManager.__repr__ and __str__ must return a constant redacted value such as <SessionKeyManager redacted>, never key bytes, hex strings, salts, passphrases, or PRAGMA statement text.
  • Connection PRAGMA Sequence: Every connection must be keyed immediately after opening through the key manager wrapper: 
    conn = sqlcipher3.connect(str(db_path))
key_manager.apply_sqlcipher_key(conn, db_name)
conn.execute("PRAGMA journal_mode = WAL;")
conn.execute("PRAGMA synchronous = NORMAL;")
conn.execute("PRAGMA busy_timeout = 5000;")
conn.execute("PRAGMA foreign_keys = ON;")
conn.execute("SELECT count(*) FROM sqlite_master;") # Lazy eval verify
  • Keying Exception Boundary: apply_sqlcipher_key() constructs and executes the PRAGMA key statement in a narrow internal scope. If any exception occurs while applying or verifying the key, it raises a generic DatabaseKeyingFailed error with database identity and recovery category only. The raised exception message, __cause__, telemetry payload, and user-facing recovery text must not include key material, the PRAGMA statement, local variables, raw driver exception text, or tracebacks.
  • Connection-Per-Thread: Separate database connection objects are opened per thread/background job and closed on completion. Connections are never shared across threads to avoid transaction collision.
  • WAL Mode: Write-Ahead Logging is enabled for all databases to allow concurrent readers without blocking writes. WAL files are encrypted using the same key as the main database.
  • Schema Migration: Numbered SQL migration scripts (e.g. 0001_init.sql) are run sequentially on startup by a custom migration manager. Migrations are idempotent and run inside a transaction.
  • Backup Strategy: VACUUM INTO is called for online same-key backups. Different-key exports use the sqlcipher_export() API.
  • Key Rotation Mechanics (SEC-009): The passphrase-change flow (§02) re-keys by export and swap, never in place. For each database: the live file is opened under the old key, a staged file under APP_INTERNAL_DIR/databases/rotation-<timestamp>/ is ATTACHed with the new key, content is copied via sqlcipher_export() (the same API already used for different-key backup exports — no new dependencies), and the staged copy passes PRAGMA integrity_check before it counts as staged. PRAGMA rekey is deliberately not used: it re-encrypts pages in place, so a crash mid-rekey can leave a file readable under neither key with no clean rollback, whereas export-and-swap leaves the original untouched until the §06 commit point. Salts are always regenerated on rotation (a salt shares its key's lifetime, and fresh salts guarantee fresh keys even for related passphrases); the staged 192-byte salts.dat is swapped in the same committed batch as the staged databases, never separately — the salts file and the database files must never be observable in a mixed old/new state. All connections are closed before the swap, and after it a new SessionKeyManager is constructed for the new keys; key managers are never mutated in place. Failures during staging follow the keying exception boundary above: no key material, salts, or PRAGMA text in any exception, log, or journal entry.
  • Relock Support: SessionKeyManager exposes a relock() operation that closes registered connections and drops all derived key material from process memory (best-effort clearing; Python cannot guarantee memory scrubbing, consistent with §02's threat model). After relock(), any keying request raises DatabaseKeyingFailed until a new unlock derives keys again.

04Cross-Platform FoundationsComplete▶

A single-repository layout with a unified application path model (APP_INTERNAL_DIR) that stores all internal SQLCipher databases, keys, configuration, logs, and assets securely under OS-standard app data directories, while user files are read directly from their original filesystem paths.

  • Single-Repo Rationale: Keeps logic, frontend, and build configuration aligned, ensuring dependency changes or platform adaptations are version-controlled atomically without Git submodule overhead.
  • platform/paths.py Responsibility: Single source of truth for all paths. Defines APP_INTERNAL_DIR (hidden, OS-standard app data root) and all derived child paths. Uses strictly pathlib.Path. User vaults/documents are referenced dynamically via absolute local paths stored in the databases.
  • APP_INTERNAL_DIR (hidden — OS-standard, all application storage):
    • Linux: pathlib.Path.home() / ".local/share/lilith"
    • macOS: pathlib.Path.home() / "Library/Application Support/Lilith"
    • Windows: pathlib.Path(os.environ["LOCALAPPDATA"]) / "Lilith"
    Contains: config.json, lilith.lock, databases/ (the 6 encrypted SQLCipher databases + salts.dat), logs/, models/, cache/, backups/, and skills/ (internal pre-approved skills). Never shown to the user.
  • File Access Model: User documents and Obsidian vaults are never staged or copied to a local staging folder. Lilith operates purely as a custodian, reading source files directly from where they live based on database pointers. The files/ staging folder is retired.
  • EXTERNAL_BACKUP_DIR (visible — user-chosen, exported/mirrored backup sets only, SEC-019): The one user-visible path Lilith writes to, in deliberate contrast to APP_INTERNAL_DIR: it exists precisely so that backup sets survive deletion of the app directory (uninstall, disk cleanup, disk failure — §06 Residency & Failure Domain). Defined in platform/paths.py as the default destination for §29 manual exports and the optional §06 automated mirror; the user may change it in Settings → Backups (stored in config.json as backup.external_destination, an absolute path that must resolve outside APP_INTERNAL_DIR — a destination inside APP_INTERNAL_DIR is rejected at entry, since it would recreate the shared failure domain this path exists to break).
    • Linux: pathlib.Path.home() / "Documents/Lilith Backups"
    • macOS: pathlib.Path.home() / "Documents/Lilith Backups"
    • Windows: pathlib.Path.home() / "Documents" / "Lilith Backups" (resolves under %USERPROFILE%\Documents; if the OS redirects Documents — e.g. OneDrive folder backup — exported sets land in a synced folder, which is acceptable per §29's synced-folder note: sets contain ciphertext + salts and the master passphrase is their only protection)
    Permissions: Created on first use with 0700 directories / 0600 files on POSIX. On filesystems that cannot honor POSIX modes (FAT/exFAT, some network mounts) the permission call is best-effort and its failure does not abort an export — for exported data the protection boundary is the set's encryption, not directory permissions (§02 threat model: backup leakage). On Windows, created files inherit the destination folder's user-profile ACLs. Layout: manual exports at the destination root as backup-<timestamp>/ (never auto-deleted by Lilith); automated mirrored sets under automatic/ (same set format; §06 retention applies).
  • Plaintext Logs Boundary: logs/ is plaintext operational storage only. It may contain startup markers, process health, migration phase names, and sanitizer-confirmed error categories, but must never receive user-authored content, conversation turns, retrieved context blocks, LLM prompts or completions, OAuth tokens, API keys, raw exception tracebacks, locals dumps, SQL statements containing key material, or serialized UCL payloads. Full-disk encryption is the documented protection boundary for OS-level crash dumps and swap; application logging hygiene does not attempt to zeroize Python heap strings after process crash.
  • POSIX & Windows Permissions: The APP_INTERNAL_DIR directory tree is created with strict POSIX permissions: 0700 for directories, 0600 for files. On Windows, per-user profile ACLs are enforced to prevent other local accounts from accessing the files. Startup checks verify and tighten permissions.
  • Resolutions for the Three Hard Windows Problems:
    1. Build Toolchain: Mitigated by standardizing on pre-compiled wheels (e.g. sqlcipher3-wheels, sounddevice with bundled PortAudio dlls, ctranslate2). MSVC compilation instructions are documented in the repo as a fallback.
    2. Audio Driver Variance: sounddevice wraps PortAudio to query WASAPI shared mode endpoints, bypasses legacy MME drivers to minimize latency, and handles device dropouts gracefully via stream restart loops.
    3. Orb Overlay Behavior: Windows transparent overlay (MiniOrb) window handles focus stealing and click-through by combining Qt flags (Qt.WindowType.FramelessWindowHint | Qt.WindowType.WindowTransparentForInput | Qt.WindowType.WindowStaysOnTopHint) with native Win32 calls using ctypes to set WS_EX_TRANSPARENT and WS_EX_NOACTIVATE.
  • Platform Detection: Evaluated once on startup using sys.platform (storing flags IS_LINUX, IS_MAC, IS_WINDOWS in lilith.platform). No ad-hoc, runtime environment variable checks allowed in feature code.
  • POSIX Heritage & Testing Strategy: Linux and macOS share POSIX heritage (common path separators, terminal signals like SIGTERM, and file lock structures). Standard tests run on Linux first, macOS is verified as a fast follow, and Windows is validated via remote GitHub Actions runners with mock audio/keyring mocks.

05Hardware Detection & Capability TiersComplete▶

A hardware profile is generated once on application startup to assign the host to Tier 0, 1, or 2, which dynamically gates local model allocation and routing.

  • Hardware Tier Definitions:
    • Tier 0 (Low VRAM/CPU-only): < 8 GB VRAM. Whisper base STT (int8 CPU) and Kokoro TTS on CPU. All LLM inference (conversational and artifact paths) routes to cloud (Anthropic).
    • Tier 1 (Mid VRAM): 8 GB to 20 GB VRAM (e.g. RTX 3060 12GB, Apple M-series with 16GB+ unified RAM). Whisper small STT (float16 GPU) and Kokoro TTS. Conversational LLM runs locally (8B model); artifact-mode LLM routes to cloud.
    • Tier 2 (High VRAM): ≥ 20 GB VRAM. Whisper small STT and Kokoro TTS. All LLM inference (conversational and artifact paths) runs locally.
  • Detection Mechanisms:
    • Windows/Linux (NVIDIA): subprocess query to nvidia-smi --query-gpu=memory.total --format=csv,noheader,nounits with a strict 1000ms execution timeout, parsing VRAM directly in MB.
    • macOS (Apple Silicon): Unified memory size query via sysctl hw.memsize. Unified memory behaves as both system memory and VRAM.
    • System RAM: psutil.virtual_memory().total to verify minimum memory availability (16GB required for local LLM execution in Tier 1+).
  • Detection Timing & Scope: Runs once during the early boot sequence (before the databases or UI are initialized). The result is stored as an immutable CapabilityProfile dataclass in the in-memory session state (lilith.platform.session_state). It is never saved to the database.
  • Hardware Support & Detection Scope Statement:
    • Supported Scope at Launch: Hardware detection and acceleration are verified and actively supported only for NVIDIA GPUs (on Windows/Linux via nvidia-smi) and Apple Silicon (on macOS via unified memory size query).
    • Other Hardware (AMD, Intel Arc, etc.): Detection for non-NVIDIA/non-Apple Silicon GPUs is not implemented at launch; such hardware will return no VRAM during detection and implicitly fallback to Tier 0 (CPU-only/Cloud). Acceleration on these platforms is "best effort, unverified" and unsupported in v6 v1 due to developer QA hardware constraints.
    • Post-Build Verification Checklist: As Apple Silicon (M1/M2/M3) unified memory graphics acceleration via Metal has not yet been physically tested by the sole developer, a mandatory post-first-build checklist item requires verifying Whisper/Kokoro Metal performance on an actual M1 machine before the official release.

06Process Lifecycle & RecoveryComplete▶

Lilith manages single-instance execution via a PID lockfile, operates a strictly ordered 10-phase startup sequence, and recovers from prior crashes via non-destructive, consensual backup restoration and quarantine.

  • Single-Instance Lock: Stored at APP_INTERNAL_DIR/lilith.lock. On boot, the app opens this file and attempts to acquire an exclusive OS-level lock (using fcntl.flock on POSIX, msvcrt.locking on Windows). Lock acquisition success is the sole authoritative source of truth that no other instance is running. If lock acquisition fails, the application displays a dialog stating "Lilith is already running" and exits immediately. When lock acquisition fails, the system reads the stored PID from the lock file and checks if a process with that PID exists and matches the application name (via psutil) only to enrich the user-facing dialog message, never to gate or decide the startup refusal itself, avoiding false-positive blocks due to post-crash PID reuse.
  • Ten-Phase Startup Sequence (Launch to Audio Ready):
    1. Phase 1 (Hardware Profile): Detect VRAM/RAM, assign capability tier (stored in-memory).
    2. Phase 2 (Process Lock): Acquire lilith.lock, write current process PID. Verify 0700/0600 folder and file permissions.
    3. Phase 3 (Keyring Verification): Verify secure OS keyring backend availability.
    4. Phase 4 (Salt Loading): Load salts.dat from APP_INTERNAL_DIR/databases/salts.dat. If databases exist but salts.dat is missing, halt startup with a recovery error screen ("Salts missing — restore salts.dat from backup to recover access"). If salts.dat is absent and no database files exist either, Phase 4 generates nothing: the run proceeds to the §25 classification (first run, reinstall-detected row (f), or restore-from-backup) with the directory state untouched. Salts are created via os.urandom(192) only inside onboarding's clean-install path (§25 Step 5), arrive as part of a restored backup set (§25 restore flow), or are regenerated by the passphrase-change flow (§02/§03) as fresh salts staged and swapped inside the rotation journal's committed batch — never eagerly during startup phases, where premature generation would manufacture local key material and mask the reinstall-detected state (§02's no-database-files rule scopes to startup/onboarding classification and is not violated by rotation's staged regeneration; SEC-025).
    5. Phase 5 (Unlock Mode Resolution): Run the §25 prompt-compatible startup detection. Convenience mode reads master_passphrase from keychain; prompt mode asks the user to type it; missing master_passphrase with existing databases is credential recovery, not first-run onboarding.
    6. Phase 6 (Database Mounting): Derive keys via Argon2id. Connect to all 6 SQLCipher databases (located at APP_INTERNAL_DIR/databases/), run PRAGMA key and verify with a dummy query. If keying fails, halt and prompt for passphrase re-entry; never delete the databases.
    7. Phase 7 (Database Migrations): Execute idempotent migration scripts in a transaction. Take an automated pre-migration backup before starting.
    8. Phase 8 (Scheduler Launch): Initialize APScheduler and register background cleanup/sync jobs.
    9. Phase 9 (Voice Pipeline Init): Load Whisper and Kokoro model files; open Sounddevice Streams.
    10. Phase 10 (Application Active): Render PySide6 window, play a short welcome chime, and transition Orb to idle.
  • Graceful Shutdown Sequence:
    1. Stop mic capture stream immediately (close Sounddevice inputs).
    2. Shut down the APScheduler scheduler (scheduler.shutdown(wait=True) to allow active jobs to exit).
    3. Abort any in-flight LLM HTTP queries.
    4. Close all database connections (flushing WAL journal logs).
    5. Release and delete lilith.lock.
    6. Exit process (status 0).
  • Automated Backups (SEC-011):
    • Trigger & Schedule: Automated backups are taken daily (via a background job scheduled at 03:20) and immediately prior to running database migrations (Phase 7).
    • Set Composition: Backups are atomic packages containing all 6 databases + the matching salts.dat + a non-secret backup.manifest.json (set format version, creation timestamp in UTC, app version, and per-file name/size/SHA-256 — never passphrases, keys, or other key material), stored in a timestamped folder under APP_INTERNAL_DIR/backups/backup-<timestamp>/. The manifest is what makes completeness and copy integrity mechanically checkable at mirror and restore time (§25 restore-from-backup flow). Manual exports via the §29 backup tool produce the identical set format.
    • Verification: Immediately after creation, Lilith performs PRAGMA integrity_check on all backed-up database files. If any checks fail, the backup is deleted and error.backup.verify_failed is logged as a critical error.
    • Retention: Lilith retains the 7 most recent valid backup sets, deleting older ones automatically. The same 7-set retention applies independently to mirrored sets under EXTERNAL_BACKUP_DIR/automatic/ — Lilith prunes only sets there that match her naming and manifest format. Manual exports at the destination root are never auto-deleted.
    • Residency & Failure Domain (SEC-019): Internal sets under APP_INTERNAL_DIR/backups/ share one failure domain with the primary databases: uninstall, disk failure, or deletion of the app directory destroys the store and every internal backup of it in a single operation. Internal sets are therefore the fast recovery path for corruption and rotation rollback (state row (c), §25; §02 rotation preflight) — they are not durable protection. Durable protection is an exported or mirrored set at EXTERNAL_BACKUP_DIR (§04); §29 defines the recovery unit (exported set + the master passphrase in effect when it was taken).
    • External Mirror (optional setting, SEC-019): When Settings → Backups → "Also keep backups outside Lilith" is enabled (off by default; surfaced by the §29 export reminders), each successful automated backup is additionally copied to EXTERNAL_BACKUP_DIR/automatic/ and verified by re-hashing every copied file against the set's backup.manifest.json. A mirrored set that fails hash verification is deleted from the destination and the copy is treated as a mirror failure; the verified internal set is unaffected.
    • Mirror Unavailability (normative): The internal backup is never gated on the mirror: it is created and verified first, and succeeds or fails on its own regardless of the external destination's state. If the destination is unavailable or the copy/verification fails (unmounted drive, deleted folder, permission error, full disk), Lilith logs error.backup.mirror_failed (reason code), surfaces a non-blocking notice in Settings → Backups, and retries at the next scheduled backup. After 3 consecutive mirror failures the notice becomes a persistent warning that remains until a mirror succeeds or the user disables the setting. Mirroring is never silently disabled, and a mirror failure never blocks, delays, or aborts the internal backup.
    • Backup UCL events (error.* namespace, §16): error.backup.verify_failed, error.backup.mirror_failed (reason), error.backup.export_failed (reason). Payloads carry set id, trigger (daily|pre_migration|pre_rotation|manual_export), location class (internal|external), sizes, durations, and reason codes only — never key material (§16 sanitizer gate). Successful backup/mirror/export timestamps are recorded in config.json for the Settings → Backups panel (§29) rather than as new UCL namespaces.
  • Crash Recovery & Consensual Restore (SEC-004 / SEC-011): At startup, if the lockfile exists but the PID inside is dead, a crash is assumed and Lilith cleans the lock. Startup then branches based on the state of the databases, salts, and onboarding marker (see state table in §25).
    • State Machine Gating: Startup distinguishes between setup crashes (a), key failures (b), and structural database corruption (c). In case of keying failure (b), databases are never touched or deleted, and the user is directed to the salts/passphrase recovery path.
    • No Silent Restoration: If structural corruption is detected (c) on one or more databases, Lilith does NOT silently restore or overwrite files. She presents a recovery screen offering per-database restoration from the latest valid atomic backup set (containing all 6 databases + matching salts.dat), showing the backup timestamp and data-loss interval.
    • Quarantine by Default: Prior to any destructive clean restart or database restore, the affected files (partial databases, salts, or corrupt databases) are moved to a quarantine folder (APP_INTERNAL_DIR/databases/quarantine-<timestamp>/) rather than being deleted outright.
    • Recovery Logs: Every recovery action, including corruption detections, quarantine moves, clean setup restarts, and restorations, is logged as an error.recovery.* UCL telemetry event (e.g., error.recovery.onboarding_crash, error.recovery.corruption_detected, error.recovery.quarantine_created, error.recovery.database_restored).
    • Restore Entry Point (fresh install / reinstall, SEC-019): The corruption recovery above restores from internal sets on a machine that still has a live store. Recovering onto a machine with no local store — new machine, OS reinstall, post-uninstall — is a different flow: the §25 restore-from-backup entry point, reachable from the first-run welcome screen and from the reinstall-detected state row (f), which verifies and places an exported set from EXTERNAL_BACKUP_DIR or any copy of one.
  • APScheduler Lifecycle: Instantiated and started in Phase 8 (right after migrations). Closed as the first step of graceful shutdown.
  • Passphrase Rotation Journal & Crash Resume (SEC-009):
    • Journal: The passphrase-change flow (§02) maintains APP_INTERNAL_DIR/databases/rotation.journal — a small non-secret JSON file recording the staging directory name, per-database staging progress, and the current phase (verify → preflight → stage → commit → finalize), written with atomic write-then-rename and fsync at each phase transition. It never contains passphrases, salts, keys, or PRAGMA text.
    • Commit point: Writing phase commit to the journal is the point of no return. Before that write, the live databases and salts.dat are untouched and the staged files are disposable. After it, the staged files are authoritative and the swap proceeds by renames: all old files (6 databases + salts.dat) move to databases/quarantine-rotation-<timestamp>/, then all staged files (including the staged salts.dat) move into place as one batch.
    • Startup resolution (Phase 4 pre-step): Before loading salts.dat, Phase 4 checks for rotation.journal. This check precedes every other state classification (including the missing-salts halt), because a mid-swap crash can legitimately leave salts.dat in transit. If the journal phase is earlier than commit: roll back — delete the staging directory and the journal; the live store is untouched and the user is told: "A passphrase change didn't finish. Nothing was changed — your previous passphrase is still in effect." If the journal phase is commit or later: roll forward — complete any remaining renames (each rename is idempotent and resumable from the journal's per-file record), prompt the user for the new passphrase, verify it opens all six databases, then in convenience mode write it to the keychain (the final step, per §02), delete the journal, and continue startup. The verified passphrase is handed to Phase 5 in memory so the user is not prompted twice. Both outcomes are deterministic; see the §25 state-table rows (d) and (e). If rotation.journal is present but unreadable or unparseable (disk-level corruption of the journal itself — unlikely given its atomic write-then-rename discipline, but reachable), neither branch applies: startup routes to the §25 explicit recovery screen — never auto-rollback, never auto-resume, never delete — with the journal, the staging directory, and any quarantine contents preserved untouched for manual recovery (SEC-028).
    • Cleanup: After a successful finalize, the old-key files in quarantine-rotation-<timestamp>/ are deleted — the preflight backup set (under the old passphrase) remains the restore point and ages out via normal retention.
    • UCL events (security.rekey.*, §16): security.rekey.start, security.rekey.backup_created, security.rekey.export_complete (db_name), security.rekey.commit, security.rekey.keychain_updated (convenience mode only), security.rekey.complete, security.rekey.rolled_back, security.rekey.resumed. Payloads carry phase, database name, and durations only — never key material (§16 sanitizer gate, §03 exception boundary). While connections are closed during the swap window no UCL events can be written; the journal is the authoritative record for that window and event logging resumes after reopen.
  • Backups Across Rotation (SEC-009): Each backup set is self-contained (6 databases + the matching salts.dat) and remains encrypted under whichever master passphrase was in effect when it was taken; retained sets are never re-keyed retroactively. Restoring a pre-rotation set is supported: the restore flow warns "This backup was taken before your last passphrase change — enter the passphrase that was in use when it was taken," verifies that passphrase against the set before restoring, and restores the set's own salts.dat with it; the store then operates under that older passphrase, and in convenience mode the restore commit writes the verified older passphrase back to the keychain so the keychain and databases never disagree. The rotation flow pauses the daily backup job for its duration (no backup can capture a mid-rotation state) and takes a fresh post-rotation backup at finalize, so the newest retained set always matches the current passphrase. Retention (7 most recent valid sets) is unchanged by rotation.

07CI/CD PipelineComplete▶

A GitHub Actions matrix runs build-and-test sequences across Linux, macOS, and Windows, generating platform-specific packages via PyInstaller --onedir mode to guarantee LGPL Relinking compliance.

  • Pipeline Triggers: Executes automatically on push to the main branch and on all pull_request events targeting main.
  • Multi-Platform Runner Matrix:
    • ubuntu-latest (Linux AppImage output)
    • macos-latest (macOS Apple Silicon/Intel .dmg output)
    • windows-latest (Windows x64 installer/.exe output)
  • Standard Build Steps (All Jobs):
    1. Checkout code via actions/checkout@v4.
    2. Set up Python 3.12 via actions/setup-python@v5 (pip cache enabled).
    3. Install dependencies via pip install -r requirements.txt (prefer-binary flag active for C extensions).
    4. Run test suite via pytest --timeout=60 -v (skips hardware-bound audio/keyring tests).
    5. Compile resources via pyside6-rcc lilith/ui/resources.qrc -o lilith/ui/resources_rc.py.
    6. Run PyInstaller via pyinstaller lilith.spec --onedir.
    7. Upload compiled directory as build artifact via actions/upload-artifact@v4.
  • Windows Build Environment: The windows-latest runner utilizes its pre-installed MSVC C++ Build Tools to resolve source compilations if wheels fail. Developer signing keys are injected securely via GitHub Secrets.
  • PyInstaller Hidden Imports: The lilith.spec includes explicit hidden imports required for runtime resolution: ["PySide6.QtOpenGLWidgets", "moderngl", "sqlcipher3-wheels", "ctranslate2", "sounddevice"].
  • LGPL Relinking Compliance: Distributing using --onedir (One-Folder mode) is a strict requirement. It keeps Python source bytecode (compiled to .pyc) and native PySide6 dynamic libraries (.so / .dylib / .dll) as separate files. This enables end-users to swap out the Qt binary files with modified versions, complying with the GNU LGPL v3 license.
  • Security Tooling Jobs (mandatory from Sprint 1): A dedicated security job group runs on ubuntu-latest only — static analysis is platform-independent, so it does not enter the 3-OS build matrix and never pays the 10× macOS/Windows runner cost — executing in parallel with the build matrix. All four jobs are required status checks: a failure blocks merge to main exactly as a failing build or test does (this is the §07 counterpart to §08's merge-blocking CI tests; the two do not overlap — §08 gates behavioural test coverage, §07 gates static security posture). None of these jobs require or receive production credentials, keychain material, SQLCipher passphrases, or BYOK cloud LLM keys — they are static readers of source and dependency metadata. The only token in scope is the auto-provided, ephemeral GITHUB_TOKEN (checkout and annotation posting); any token a job ever needs is supplied through GitHub's encrypted-secrets mechanism and never committed to a file, consistent with §02's keychain-only / no-secrets-in-files standard.
    1. bandit — Python SAST over the source tree: runs bandit -r lilith/ -c pyproject.toml on every push and every pull_request. Baseline configuration lives in a [tool.bandit] table in pyproject.toml (single source of truth, versioned with the code). Gate: findings at HIGH severity with ≥ MEDIUM confidence block the merge; MEDIUM severity is surfaced as a warning annotation; LOW severity/confidence is informational only. Suppression: a specific inline # nosec BXXX — <justification> comment naming the rule id and the reason; a rule-less blanket # nosec is rejected in review.
    2. semgrep — multi-rule SAST: runs semgrep ci --config=auto --error on every push and every pull_request. --config=auto selects the community-registry ruleset matched to the repository's languages; it runs with no SEMGREP_APP_TOKEN and no login, uploads no source, and transmits only anonymous language/framework metadata to select rules. Gate: ERROR-severity findings block the merge; WARNING/INFO warn only. Suppression: an inline # nosemgrep: <rule-id> — <justification> comment, or a path entry in .semgrepignore carrying a justifying comment.
    3. pip-audit — dependency vulnerabilities: runs pip-audit -r requirements.txt --strict on every push and pull_request, and additionally on a weekly schedule trigger to catch advisories newly disclosed against unchanged, already-merged pins. Gate: any advisory for which a fixed version is available blocks the merge; an advisory with no upstream fix warns and is tracked through an explicit --ignore-vuln <ID> entry that carries a comment (advisory id plus why it is unfixable or not reachable in Lilith's usage), re-reviewed at every dependency bump. Suppression: the --ignore-vuln allowlist only; there is no blanket disable.
    4. gitleaks — secret scanning over the repo and history: on every push and pull_request it scans the incoming commit range (fast, PR-scoped); on push to main and on a weekly schedule it scans the full history (--log-opts="--all"). This split keeps per-PR runs cheap while guaranteeing a periodic whole-history sweep so a secret introduced and later force-pushed away on a branch is still caught, and any historical leak that slipped past a diff scan is surfaced. Baseline is the default gitleaks ruleset, optionally extended by a repo .gitleaks.toml. Gate: any finding blocks the merge — a committed secret has no "low severity" tier. Suppression: a fingerprint line in .gitleaksignore with a trailing justification comment, or an inline gitleaks:allow on a confirmed false positive.
  • Anti-Rot Triage Discipline: Every suppression across all four tools is (a) per-finding, never a blanket disable; (b) co-located with the flagged code or committed as a tracked config line; (c) accompanied by a written justification; and (d) therefore visible in the pull-request diff and reviewed before merge. Disabling a security job, deleting its severity gate, or committing a rule-less blanket suppress is a spec violation, not a shortcut. A per-sprint suppression audit greps for nosec, nosemgrep, .semgrepignore, --ignore-vuln, and .gitleaksignore entries and re-confirms each justification still holds, removing stale ones so the gate cannot silently rot into ignore-everything. The severity thresholds are deliberately tuned to the true-positive tier of each tool (bandit HIGH+MEDIUM, semgrep ERROR, pip-audit fixable-only, gitleaks any) so the gate is cheap enough for a solo developer to keep enabled rather than route around — an over-noisy gate that gets disabled protects nothing.

08Testing StandardsComplete▶

A strict testing framework uses pytest, enforces timeouts, bans database mocking by testing against real SQLCipher connections, and mandates telemetry assertions for all write paths.

  • Test Execution Timeouts: Enforced to prevent CI hangs. Fast unit sweeps are run via timeout 60 pytest tests/unit/, while the full test suite runs via timeout 180 pytest. A known pre-existing stall in the full-suite interface API tests is acknowledged and temporarily bypassed during CI sweeps.
  • No-DB-Mocking Policy: Unit and integration tests must run against real SQLCipher databases, not mocked database objects (which cause v5 bugs like lazy evaluation crashes to be missed). A conftest.py fixture creates an in-memory SQLCipher database, keys it with a fixed test passphrase, runs migrations, and tears it down after each test.
  • LLM Testing Integration: Cloud LLM providers are not mocked. Instead, tests utilize canned JSON fixtures matching the provider's exact payload schema. Live integration tests can optionally run if the ANTHROPIC_API_KEY environment variable is set on the runner.
  • UCL Telemetry Assertions: Every test covering a write path must assert that the correct dot-namespaced UCL event was emitted. The log_event() function is mocked or wrapped via a custom test handler to record emitted events for validation: 
    def test_create_contact(db_conn, mock_ucl):
    contact_id = contacts.create(db_conn, name="Steven")
    assert mock_ucl.has_event("contacts.write.created", {"contact_id": contact_id})
  • Payload Schema Review: Every new UCL event must declare its payload fields explicitly in the event schema before implementation. Review must reject catch-all message, context, prompt, traceback, locals, or arbitrary JSON payload fields unless a named exception is approved in the design session. Free-text user content, conversation turns, retrieved context blocks, and LLM-visible prose belong in conversation_db or the source domain database, not in UCL event payloads.
  • Test Layout Directory Mirroring: Tests mirror the source structure exactly:
    • tests/unit/: Fast, isolated tests for individual functions and classes. Uses LLM response fixtures; mock-free except for external APIs.
    • tests/integration/: Multi-component workflows, real database migrations, and optional external API queries. Skipped if necessary credentials are missing.
  • Sprint Done-Criteria Standard: Writing a new database insert or mutation function requires delivering a corresponding test that asserts its UCL event emission and validates the event payload against the declared schema before the PR can be merged.
  • Backup→Wipe→Reinstall→Restore Drill (SEC-019, mandatory CI): tests/integration/test_backup_restore_drill.py is a required, merge-blocking CI test that exercises the full §29 recovery unit end-to-end against real SQLCipher files (no DB mocking, per policy), with the keyring mocked per existing integration conventions. Steps: (1) build a temp APP_INTERNAL_DIR store — all 6 databases keyed with the fixed test passphrase and seeded with known fixture rows, plus salts.dat; (2) export a backup set to a temp external destination through the §29 backup-tool code path, recording per-table row counts and the set's backup.manifest.json hashes; (3) delete the entire temp APP_INTERNAL_DIR (simulated uninstall); (4) create a fresh temp APP_INTERNAL_DIR (simulated reinstall) and run the §25 restore-from-backup flow programmatically against the exported set; (5) open the restored store with the test passphrase. Pass criteria: all six restored databases open with the passphrase and pass PRAGMA integrity_check; per-table row counts equal the pre-wipe counts; restored file hashes match the manifest; salts.dat is byte-identical to the exported copy. The drill additionally asserts the §25 failure paths: a wrong passphrase and a deliberately incomplete set must each refuse the restore, leave the exported set unmodified, and emit error.recovery.restore_failed with the correct reason code.
  • PII Detector Recall Corpus (SEC-018, mandatory CI): The §14 cloud-PII detector is gated by tests/unit/test_pii_detector_recall.py, a merge-blocking unit test that measures detection recall against the fixture corpus tests/unit/fixtures/pii_corpus.json (following the §08 fixtures/ convention). Corpus growth rule: when a recall failure is observed in dogfooding, adding the failing case (or an anonymized equivalent) to the corpus is required as part of the fix, and the fix must restore the thresholds before merge. 09Audio I/O & Platform Audio APIsComplete▶

Audio I/O is managed using the sounddevice package with PortAudio, separating capture and playback callbacks onto dedicated worker threads, using WASAPI shared mode on Windows, and handling device disconnections via automatic recovery loops.

  • Audio Library Choice: sounddevice + PortAudio (MIT licensed). Offers robust, cross-platform wheels containing pre-compiled PortAudio binaries, avoiding legacy compilation bugs common with PyAudio on modern Python versions.
  • Microphone Stream (Capture): sounddevice.InputStream callback is locked to 16 kHz mono float32 with a block size of 480 frames (30ms). The callback only copies the chunk and pushes it to a thread-safe audio_q queue. No allocations or model inference may run on this thread.
  • TTS Playback Stream (Output): sounddevice.OutputStream runs at 24 kHz mono float32 with a block size of 1024 frames, pulling compiled audio segments from a bounded playback_q. Playback runs concurrently and independently of capture.
  • Windows WASAPI Integration: The device manager queries and binds to the WASAPI Host API index. Runs in WASAPI Shared Mode by default to prevent exclusive-access locks that conflict with other desktop applications (browsers, Discord).
  • Resampling Fallback: If a microphone device rejects native 16 kHz capture, Lilith opens the hardware stream at the default native rate (44.1 kHz or 48 kHz) and resamples the captured chunks down to 16 kHz in the VAD thread using numpy.interp before processing.
  • Stream Restart & Hot-Plug Recovery: The audio manager handles stream exceptions or status flags (underflow/overflow) by closing the active stream, executing device re-enumeration, selecting the system's new default device, and restarting the stream.
  • Device Diagnostics: A developer diagnostics widget allows device enumeration, latency loopback measurements, and manual channel overrides. Exposes real-time RMS amplitude values to the Orb widget.

10Speech-to-Text (STT)Complete▶

Speech-to-Text uses faster-whisper with a CTranslate2 backend, dynamically scaling the model size by hardware tier, and filtering stream input via Silero VAD on a dedicated worker thread.

  • Python Package & Backend: faster-whisper (v1.2.1) utilizing the CTranslate2 backend. Permissively licensed under the MIT license, allowing for closed-source commercial redistribution.
  • Model Selection by Tier:
    • Tier 0: base model (int8 quantized) executed on the CPU, maintaining a <1.0s transcription latency.
    • Tier 1 & 2: small model (float16 quantized) executed on CUDA GPUs or optimized CPU paths (Apple Silicon NEON), balancing high accuracy with a <0.5s transcription latency.
  • Silero VAD Parameters:
    • Input chunk size: 480 frames (30ms at 16 kHz sample rate mono float32).
    • Speech threshold: 0.5 (probability cutoff).
    • End-of-speech window: 600ms of contiguous silence (min_silence_duration_ms=600).
    • Padding: 250ms pre/post padding (speech_pad_ms=250) to ensure word boundaries are not truncated.
  • Speech Pipeline Architecture:
    1. sounddevice.InputStream pushes 30ms audio chunks to audio_q.
    2. The VAD worker thread pulls chunks, calculates speech probabilities, and buffers speech frames.
    3. When VAD triggers end-of-utterance, the buffered frames are concatenated into a single NumPy array and dispatched to the transcription_q.
    4. The Whisper worker thread pops the array, transcribes it in a batch, and sends the raw string to the two-mode router.
  • Output Structure: A single plain text string. Downstream components (the router) receive the string directly without metadata or timestamp arrays.
  • UCL Telemetry Events:
    • voice.stt.start: Emitted when the VAD identifies speech starting.
    • voice.stt.complete: Emitted on successful transcription. Payload includes: duration_ms (processing latency), audio_len_ms (utterance length), and word_count.

12LLM Integration & Provider AbstractionComplete▶

Lilith v6 uses a small in-house async provider adapter, with Anthropic as the BYOK primary provider and Ollama as the Tier 1/2 local fallback.

  • Adapter contract: complete(messages: list[dict], system: list[dict], stream: bool = True) -> AsyncIterator[str]; one implementation per provider, no LiteLLM in v6 v1.

  • Ollama fallback: Use the OpenAI-compatible local endpoint through openai==2.44.0 with base_url="http://127.0.0.1:11434/v1" (the base URL is user-configurable in config.json to support custom reverse-proxy setups; any bearer token for that proxy is a secret and is read from the OS keychain key ollama_bearer_token under service "com.squirrelthug.lilith" — §02's canonical credentials table — never from config.json); keep the selected local model warm on Tier 1/2.
  • Provider selection: Read key anthropic_api_key under service "com.squirrelthug.lilith" from python-keyring (as defined in §02's canonical credentials table); if present use Anthropic, otherwise use Ollama when hardware tier is 1 or 2, otherwise return onboarding error missing_cloud_key.
  • Budgets: Conversational mode hard cap <=1200 volatile context tokens and <=50 output tokens; artifact mode has no fixed output cap but still streams and records usage.
  • Context safety: Provider payloads receive only CWM-approved L1/L2 context; raw DB rows are never passed to complete().
  • Telemetry: Emit llm.call.start (provider, model, mode) and llm.call.complete (tokens_in, tokens_out, latency_ms, success).
  • Ollama Auto-Setup & Installer: If Ollama fallback is selected but the Ollama binary is absent, the daemon is not running, or the required local model is missing, Lilith triggers an automated setup flow. Before initiating downloads, the system presents a clear disclosure screen detailing the estimated download size (up to several gigabytes for CUDA dependencies and LLM models), estimated time, and warns that a system reboot may be required. Download and installation proceed only upon receiving explicit user consent. Progress state is persisted to a setup marker file (APP_INTERNAL_DIR/config.json) so that setup can resume automatically if interrupted (e.g., by a system restart).
  • Installer Provenance & Integrity (SEC-017): The auto-installer is the only place in the design where Lilith fetches remote code and executes it, and it is hardened accordingly. Installer binaries are downloaded exclusively from a compile-time allowlist of official Ollama HTTPS release endpoints; redirects that leave the allowlisted hosts are refused, and TLS certificate validation is always enforced with no configuration or UI override. Every downloaded artifact is verified against a pinned SHA-256 checksum or vendor signature (see the trust anchor below) before it is executed; on mismatch the artifact is deleted, the flow aborts (error.ollama.install_integrity_failed), and no "run anyway" option exists. Trust anchor (SEC-026): the reference the artifact is verified against is pinned in the application, never fetched over the same channel as the artifact. Where the platform artifact carries a vendor signature — at the time of writing, OllamaSetup.exe is Authenticode-signed on Windows and the macOS app is Developer ID-signed and notarized — the signature is verified against a signing identity pinned in the application. Where it does not (the Linux release tarballs ship unsigned), the artifact is verified against a per-release SHA-256 hash pinned in the application, updated only through app updates — themselves the developer-signed channel. A checksum fetched at runtime from the same origin as the artifact (e.g. the release's published sha256sum.txt asset) is never acceptable as the sole integrity mechanism: a compromised origin serves a tampered artifact and its matching checksum together, which is precisely the supply-chain adversary this paragraph exists to defend against. Elevation is never invoked silently — the verified installer is handed to the OS-standard elevation prompt (Windows UAC, Linux polkit, macOS Authorization Services) so the user sees what is executing. On resume after an interruption or reboot, prior consent may persist but integrity is re-proven by re-hashing the artifact before installation continues. Successful installs are audited to the UCL as sync.ollama.install_verified (installer version + verified hash). Model pulls via the Ollama registry API inherit whatever integrity Ollama's own registry mechanisms provide; that reliance is a documented, accepted dependency.
  • Ollama Endpoint Verification & Security (SEC-008): To mitigate unauthenticated localhost binding risks, Lilith performs a startup verification check (querying /api/version and confirming that the configured model exists in the local registry) before sending any context data during a session. Custom endpoints can configure a custom base URL (in config.json) and a bearer token (in the keychain as ollama_bearer_token, §02's canonical table — SEC-020: a bearer token is a credential and is never written to config.json). If verification fails or a port hijack is detected, all outbound context is blocked, and an error is logged. Composition with the §14 tokenization bypass (Fool's NC-3): because the §14 cloud-PII tokenization pass is bypassed for local inference, un-tokenized names, email addresses, and phone numbers flow to this endpoint while its verification remains best-effort — see §14's Local-Path Composition recorded decision (2026-07-12), which accepts this composition within §02's same-user threat boundary.
  • Provider Visibility (SEC-008): The application UI displays a persistent, always-visible status indicator showing the active LLM provider (Anthropic Cloud vs. Local Ollama) so the user is always aware of where their context is sent, updating dynamically upon any provider selection changes.

Functional Requirements (EARS Format)

  • When the provider selection logic falls back to Ollama, the system shall check for the presence of the Ollama binary in the system PATH (or application internal directory) and verify if the Ollama service is active.
  • When Ollama installation, service activation, or model pulling is required, the system shall present a clear disclosure screen detailing the estimated download size, download time, and a disclaimer that a system restart may be required.
  • The system shall only initiate the download and installation process after the user explicitly accepts the disclosure.
  • If the Ollama binary is absent and user consent is granted, the system shall download the installer subject to the provenance requirements below and shall run the platform-appropriate installation only after integrity verification succeeds.
  • When the Ollama daemon is running but the configured model is missing from the local registry, the system shall invoke the Ollama model pull API automatically.
  • While an installation or model pull is active, the system shall persist progress state to a setup marker file, enabling the system to resume the setup flow from the last known state if the application is restarted or the OS reboots.
  • Before sending any CWM context payload during a session, the system shall verify the Ollama endpoint by querying /api/version and checking that the target model is present in the local registry.
  • If endpoint verification fails, the system shall block all context transmission to localhost and log the verification failure.
  • Where the user opts to front Ollama with a custom reverse proxy, the system shall read the configurable base URL from config.json and shall read the optional bearer authentication token exclusively from the OS keychain (ollama_bearer_token, service "com.squirrelthug.lilith", per §02's canonical credentials table), written by Settings; the system shall never persist that bearer token in config.json or any other plaintext file.
  • The system shall display a persistent, always-visible UI indicator in the main application shell reflecting the active LLM provider.
  • If the Anthropic key is removed or fails validation, forcing a fallback to Ollama, the system shall update the provider indicator immediately.
  • The system shall download Ollama installer artifacts only from an allowlist of official Ollama HTTPS release endpoints compiled into the application; the allowlist shall not be extendable at runtime by configuration or user input.
  • If an installer download response redirects to a host outside the compiled-in allowlist, the system shall refuse the redirect, abort the download, delete any partial artifact, and log error.ollama.install_source_refused.
  • The system shall enforce TLS certificate validation on every installer download connection and shall provide no mechanism — configuration flag, environment variable, or UI action — to disable or override it.
  • Before executing any downloaded installer artifact, the system shall verify the artifact for the exact release being installed against a trust anchor pinned in the application: a vendor signature checked against an application-pinned signing identity where the platform artifact is signed, otherwise an application-pinned per-release SHA-256 hash; the system shall not treat a checksum fetched at runtime from the same origin as the artifact as the sole integrity mechanism (SEC-026).
  • If installer integrity verification fails, the system shall abort the installation without executing the artifact, delete the artifact, log error.ollama.install_integrity_failed, and display a user-facing integrity error; the system shall offer no option to execute an unverified artifact.
  • Where installer execution requires elevated privileges, the system shall request elevation exclusively through the operating system's standard elevation mechanism (Windows UAC, Linux polkit, macOS Authorization Services) so the user sees what is executing; the system shall never invoke elevation silently.
  • While a setup marker indicates an interrupted installer download or installation, when the setup flow resumes after an application restart or OS reboot, the system shall re-verify the artifact's SHA-256 hash before installation continues; persisted consent shall not substitute for re-verification, and a mismatch shall take the same abort path as a failed initial verification.
  • When installer integrity verification succeeds and installation completes, the system shall log the installer version and verified SHA-256 hash to the UCL as sync.ollama.install_verified.
  • The system shall treat model pulls performed through the Ollama registry API as relying on Ollama's own registry integrity mechanisms; this reliance is a documented accepted dependency, and the system shall not represent pulled models as independently integrity-verified by Lilith.

Acceptance Criteria (Given/When/Then)

  • AC-001 (Happy Path - Auto-Install): Given a Tier 1/2 user without an Anthropic API key and lacking Ollama, when Lilith starts up, then Lilith displays the Ollama Disclosure Screen warning of a multi-gigabyte download and potential system restart. When the user accepts, then Lilith downloads the installer from an allowlisted official Ollama release endpoint over validated TLS, verifies its SHA-256 checksum or vendor signature before execution, runs it (via the OS-standard elevation prompt where elevation is required), starts the daemon, pulls the model, displays progress, and updates the persistent UI indicator to "Local Ollama" upon completion.
  • AC-002 (Setup Resumption): Given an Ollama setup flow that was interrupted mid-download by a system reboot, when Lilith restarts, then Lilith detects the partial setup marker and resumes the model pull/installation automatically without re-prompting the user for consent; before any previously downloaded installer artifact is executed, Lilith re-verifies its SHA-256 hash and proceeds only if re-verification succeeds (a mismatch takes the AC-005 abort path).
  • AC-003 (Disk Space Failure): Given a target installation directory with less than 15 GB of available disk space, when the user accepts the Ollama installation prompt, then Lilith halts the installation, displays a disk space error message, and writes the error.ollama.disk_full event to the UCL.
  • AC-004 (Port Hijack Detection): Given an unauthorized local process bound to port 11434 that does not respond to /api/version, when Lilith attempts the startup endpoint check, then Lilith halts the connection, blocks context outflow, logs error.ollama.port_hijack, and displays a warning to the user that the port is occupied by an unexpected process.
  • AC-005 (Installer Integrity Mismatch): Given a fully downloaded installer artifact whose SHA-256 hash does not match the application-pinned per-release checksum or whose vendor signature fails validation against the application-pinned signing identity, when Lilith performs pre-execution verification, then Lilith aborts the installation without executing the artifact, deletes the artifact, writes error.ollama.install_integrity_failed to the UCL, and displays an integrity error screen that offers a fresh retry but no option to run the unverified artifact.
  • AC-006 (Off-Allowlist Source Refused): Given a download attempt whose URL or redirect chain resolves to a host outside the compiled-in allowlist of official Ollama HTTPS endpoints (e.g., a network-position attacker or a compromised/typosquatted mirror), when Lilith processes the redirect, then Lilith refuses it, aborts the download, deletes any partial artifact, writes error.ollama.install_source_refused to the UCL, and displays a source-verification error — no artifact bytes are ever executed.
  • AC-007 (Tampered Artifact on Resume): Given an interrupted setup with a persisted marker whose downloaded artifact was modified on disk during the interruption, when Lilith restarts and resumes the setup flow, then re-verification of the artifact's SHA-256 hash fails and Lilith takes the identical abort path as AC-005 — delete the artifact, write error.ollama.install_integrity_failed, display the integrity error — without executing the artifact, despite the persisted consent.
  • AC-008 (No Silent Elevation): Given a verified installer that requires elevated privileges, when Lilith launches it, then the operating system's standard elevation prompt (UAC / polkit / macOS Authorization Services) is presented to the user and installation proceeds only after the user approves at the OS level; at no point does Lilith elevate without the OS prompt being shown.
  • AC-009 (Verified Install Audit Trail): Given an installation that passed integrity verification and completed successfully, when the setup flow finishes, then the UCL contains a sync.ollama.install_verified event recording the installer version and the verified SHA-256 hash.

13Two-Mode RouterComplete▶

The router is a deterministic, rule-based gate that protects the ≤3 s conversational path by sending every tool call or long response to the artifact path.

  • Classifier: Keyword, intent, and endpoint-capability rules only; no LLM classifier runs on the critical voice path.
  • Conversational mode: Allowed only when expected spoken output is <=50 tokens, no tool call is required, endpoint supports voice response, and CWM can fit the request inside <=1200 context tokens.
  • Artifact mode: Required when a tool call is needed, expected output is >50 tokens, multi-source data is requested, endpoint cannot display the full answer inline, or CWM would exceed the conversational budget.
  • Latency budget stance: The <=3 s first-audio target, <=50 conversational output cap, and <=1200 volatile context cap are v6 v1 working hypotheses, not immutable constants. They are kept as initial router targets so the build has a concrete shape, then adjusted through daily dogfooding and the Milestone 1 validation experiments in BUILD_SEQUENCING.md: the walking-skeleton latency benchmark and the 100-utterance router dry-run.
  • Tokenization latency accounting (SEC-022 / Fool's NC-4): On a cloud provider, the conversational path includes two additional budgeted steps inside the ≤3 s first-audio target: the §14 substitution pass (after CWM assembly, before dispatch) and the §14 reverse-substitution pass (on the response stream, upstream of the §11 sentence chunker, subject to §14's partial-tag hold rule). Both are deterministic, single-pass, O(context length) local operations with no network or LLM calls. Their cost is not assumed negligible: Experiment 1 in BUILD_SEQUENCING.md runs the walking-skeleton benchmark with tokenization on vs off and records the delta, so the ≤3 s hypothesis is validated with the real pipeline in place. On the artifact path, dispatch additionally captures the §14 task-owned mapping snapshot at spawn time (an O(mappings-applied) copy). Local Ollama turns skip both passes entirely (§14 bypass; composition recorded in §14's Local-Path Composition note).
  • Milestone-1 counterfactual dry-run instrumentation: The 100-utterance router dry-run in BUILD_SEQUENCING.md is instrumented to answer two questions, not one: "how accurate is the two-mode classifier?" and "would single-path routing have handled this turn better?". Per utterance, the dry-run records the router's pre-classification decision and the specific rule that fired, then runs one uncapped, tool-enabled generation (high max_tokens, the <=50-token cap deliberately not enforced) and records: (a) the actual output token count, (b) whether a tool call was actually emitted, and (c) whether cutting the output at 50 tokens would have truncated mid-sentence. A per-turn verdict — correct_conversational, correct_artifact, misroute_to_artifact (trivial turn got the artifact ceremony), or misroute_to_conversational (answer guillotined and/or needed tool lost) — is derived mechanically from (a)–(c) per the definitions in BUILD_SEQUENCING.md §3 Experiment 2; no judgment call is involved, so two people computing the verdicts get the same answer. The utterance set MUST be assembled and frozen (SHA-256 recorded) before any router rule is tuned against dry-run results. Records are emitted as router.dryrun.* events per §16 naming; during Milestone 1, while ucl_db is deferred, they are emitted through the standard dev-log path as JSON lines.
  • Pre-committed misroute threshold (quality gate; committed 2026-07-12, before any dry-run data exists): Over the frozen utterance set, with the full set as denominator and rates reported per misroute direction: if the total misroute rate exceeds 10%, or the misroute-to-conversational rate alone exceeds 5%, the stream-and-cut fallback review named below is mandatory before persona or CWM behavior is hardened on top of the router. The threshold is fixed now, before the experiment runs, precisely so the dry-run result can falsify the two-mode choice rather than only confirm it.
  • Named fallback — stream-and-cut single-path routing (normative): If the pre-committed threshold is crossed, the documented fallback architecture is stream-and-cut single-path routing: every turn begins streaming a response immediately, with no pre-classification, and is promoted to the artifact lane only when the output actually exceeds the conversational budget or the model actually emits a tool call. Promoting mid-stream has a recorded cost at the voice endpoint: TTS may already be speaking when promotion occurs, so the user hears the beginning of a direct answer that is then abandoned or pivoted into an acknowledge-and-bridge — an audible false start on every promoted turn, which is exactly the failure mode two-mode pre-classification exists to avoid. The two-mode router remains the chosen v1 architecture; this fork stays provisional until the Milestone-1 dry-run data is in, and crossing the threshold triggers a mandatory stream-and-cut design session, not an automatic pivot.
  • Visual latency bridge: Once a conversational or artifact request has been accepted and elapsed wait time crosses 750 ms without a visible or audible response, the shell shows a compact progress affordance tied to the active turn. The affordance communicates current pipeline stage (listening, transcribing, thinking, speaking, or building artifact) and approximate remaining wait using a shrinking ring or equivalent stage indicator. It must remain visible until first audio, first text token, artifact panel creation, or a candid failure state occurs. For waits around 3-5 s, the animation should make progress legible rather than implying the app is frozen.
  • Skill context injection (artifact path): After artifact classification, the router queries the approved skill index built from APP_INTERNAL_DIR/skills/ at startup. 14Context Window ManagerComplete▶

The Context Window Manager injects only fresh, priority-ordered L1/L2 context blocks and enforces the conversational hard cap of 1,200 volatile tokens.

  • Priority order: system_identity, personal_truths, memory_recall, entity_context, then tool_context.
  • Freshness thresholds: system_identity 24h, personal_truths 7d, memory_recall 24h, entity_context 30m for calendar/contacts and 24h for memory entities, tool_context 5m.
  • Staleness gate (withheld, never silently): Blocks older than their threshold are withheld from the prompt; CWM emits context.block.withheld with reason="stale". Withholding is never silent: when the withheld (or entirely absent) block belongs to a family the turn's intent selected, CWM MUST first attempt an intent-matched refresh (below) and, if fresh data is still unavailable, MUST inject an absence disclosure (below). Serving stale data and omitting intent-relevant data without disclosure are both prohibited.
  • Intent-matched refresh: "Matching intent" is defined by the existing intent-selection table: if intent selection includes a block family for this turn and that family's block is stale or absent, the match holds — deterministic, no LLM on the voice path (§13). On match, CWM requests a targeted refresh from the enhancement layer (§17): an incremental source sync first when the source watermark is stale and the domain supports automated sync (§19), then L1 → L2 for that domain. A refresh is always a pipeline sync/enhancement trigger — the LLM never fetches live data. The wait is bounded per lane: conversational turns wait at most STALE_REFRESH_BUDGET_CONV_MS = 1000, artifact turns at most STALE_REFRESH_BUDGET_ARTIFACT_MS = 10000. Both are config.py working hypotheses in the same sense as §13's latency targets, tuned via the Milestone 1 walking-skeleton benchmark and dogfooding; 1000 ms is chosen so a successful in-turn refresh still leaves ≥2 s of the ≤3 s first-audio budget for LLM + TTS, with the §13 750 ms latency bridge covering the perceived wait. If the refresh completes inside the budget, CWM re-reads the fresh L2 summary and injects it normally. On timeout, on failure, or when the domain's refresh_capability is manual_source (§17 — reserved for future manual-import domains such as the parked finance statement import, which require user action), CWM falls back to absence disclosure while any in-flight refresh continues in the background so the next turn sees fresh data.
  • Mandatory absence disclosure: Whenever a block relevant to the turn is withheld as stale or is absent (domain never synced, refresh timed out, refresh failed, or source unsupported), the compiled context MUST include a compact machine-generated data-status notice stating: the domain, the status (stale, missing, refresh_timeout, refresh_failed, or source_unsupported), the last successful sync time when known, and an explicit statement that the data is unavailable this turn and must not be guessed. Example shape (normative content requirements, not final copy): [data-status domain=calendar status=stale last_synced=2026-07-12T09:14Z — calendar data is unavailable for this turn; do not guess or invent it; offer to refresh]. The notice is generated by CWM itself (trusted system-side content, never third-party text), counts toward the 1,200-token cap, and is never evicted or dropped for budget reasons while its domain remains intent-relevant — the eviction order applies to data blocks, not to disclosure notices.
  • Conversational cap: Total volatile context is <=1200 tokens; over-budget eviction order is tool_context, entity_context, memory_recall, then oldest conversation turns. system_identity and personal_truths are never evicted, only compacted.
  • Intent selection: Router mode and intent choose block families: small talk gets identity/truths only; person questions add entity_context; recall requests add memory_recall; artifact/tool turns add tool_context.
  • Message format: Stable EDICTS/VOICE/system identity are system content blocks; personal truths and L2 summaries are labeled assistant-context blocks. Externally-sourced L2 blocks (e.g., from Google sync, calendar invites, or contact notes) are marked with clear provenance labels (e.g., [source: google_sync - untrusted third-party text]). Tool context is injected as a provider tool-result or artifact summary, never as raw rows.
  • Cloud PII Tokenization (SEC-018 — v1 detection scope: person names, email addresses, phone numbers): On the path to a cloud provider (bypassed for local Ollama inference to minimize latency and CPU load), CWM runs the compiled context window through an in-memory tokenization pipeline:
    • PII Detector (three classes, full v1 scope): A rule-and-pattern-based detector (not an allowlist) scans the assembled prompt context for person names (rule-based; best-effort — recall is not guaranteed, particularly for unusual names, nicknames, possessives, and names inside quoted message text), email addresses, and phone numbers (both via deterministic patterns — the classes where pattern matching is reliable). This is the full v1 detection scope: merchant names, monetary amounts, health and relationship details, free-text notes, and location text outside §19's calendar-address preprocessing are not detected and egress as-is. §02's Data Hygiene paragraph is the user-facing statement of this boundary and must never claim more than this bullet specifies.
    • Substitution Pass: Every detected item is replaced with a stable, distinct tag from its class's tag family: the user becomes <principal_user> and contacts map to <contact_1>, <contact_2>, …; email addresses map to <email_1>, <email_2>, …; phone numbers map to <phone_1>, <phone_2>, ….
    • Ephemeral Mapping Table — Session Scope (SEC-022): The tag-to-value mapping (all three classes) is stored in local, volatile memory, never persisted or sent to the cloud. "Stable" means stable for the unlocked session: the mapping table shares the lifecycle of the §03 SessionKeyManager — it is created empty at unlock, the same detected value maps to the same tag for the entire unlocked session (tag counters only ever grow, never reassign), and the table is dropped in full at explicit re-lock (§02, alongside SessionKeyManager.relock()) and at app exit. Session-stable tags keep cloud-side coreference coherent across the turns of one session; after a re-lock or restart, tag counters start fresh and any tag echoed from a previous session is by definition unmapped and takes the unmapped-tag path below.
    • Reverse-Substitution Pass: Reverse substitution is applied exactly once, to the response text stream as it arrives from the cloud provider, upstream of the §11 sentence/clause chunker; every downstream consumer (TTS, the chat UI, memory, databases) receives only post-substitution text. Tags (all three families) are replaced with the true values from the session mapping table — or, for background artifact tasks, from the task-owned snapshot below. On the streaming path the pass obeys the partial-tag hold rule below.
    • Recall Done-Criterion (merge-blocking, see §08): The detector ships with the §08 fixture corpus tests/unit/fixtures/pii_corpus.json (unusual names, nicknames, possessives, names embedded in quoted message text, plus email/phone format variants). tests/unit/test_pii_detector_recall.py measures recall against the corpus in CI and is merge-blocking: person-name recall ≥ 95%, email recall = 100%, phone recall = 100%. When a recall failure is found in dogfooding, extending the corpus with the failing case is required (§08 corpus growth rule). Precision is not CI-gated in v1: over-substitution is privacy-conservative and only degrades response quality.
    • Unmapped-Tag Handling (SEC-022): On reverse substitution, a tag with no entry in the applicable mapping table (a model-invented tag, a tag echoed from a previous session after re-lock or restart, or a mapping lost to a crash) is stripped and replaced with a neutral placeholder by tag family: <contact_n> → "a contact", <email_n> → "an email address", <phone_n> → "a phone number", <principal_user> → "the user". Each replacement emits context.token.unmapped to the UCL (tags are anonymous and carry no PII, so the literal tag is a permitted payload field under §16's rules). An unmapped tag is never spoken literally by TTS, never written to memory or any database, and never bound to a guessed identity.
    • Task-Owned Mappings for Artifact Tasks (SEC-022): A background artifact task (§13) never depends on the live session table: at dispatch, the substitution pass hands the task an immutable snapshot of exactly the mappings it applied to that task's outbound payload. The task owns its snapshot until it completes or is abandoned, so an artifact that outlives UI state still reverse-substitutes correctly; a response tag missing even from the snapshot takes the unmapped-tag path above. Re-lock fails closed: §02 re-lock drops the session table and every task-owned snapshot. An in-flight artifact task holding a snapshot is cancelled at re-lock — any late response is discarded unprocessed, error.artifact.relock_cancelled (task_id, tool_name) is logged, and after the next unlock the task is reported as failed via its §15 failure narrative. No identity mapping ever survives a lock.
    • Streaming Reconciliation — Partial-Tag Hold Rule (Fool's NC-4): Because §11 releases audio sentence-by-sentence, a tag may straddle a stream chunk. The reverse-substitution scanner is a deterministic, single-pass, O(stream length) filter: text flows through freely, but when a < opens a tag candidate, the characters from that < onward are held — never released to the sentence chunker — until the candidate resolves. It resolves as a tag when it closes with > and matches the tag grammar <(principal_user|contact_N|email_N|phone_N)> (N a decimal integer); it is proven not-a-tag the moment a character outside [a-z0-9_] appears before >, when it closes with > without matching the tag grammar (e.g. <abc> or <contact_>), when it exceeds 16 characters without closing (the longest valid tag, <principal_user>, is exactly 16), or at end of stream — in every not-a-tag case the held text is released verbatim, and this enumeration is exhaustive: every candidate resolves to exactly one of substituted-as-tag or released-verbatim (SEC-027). Tags contain no sentence-ending punctuation, so a resolved tag never spans a §11 sentence boundary. Worst-case added hold: the stream time of one 16-character candidate (≈4 tokens) per occurrence, incurred only when the stream pauses mid-candidate; the measured cost is the tokenization on/off delta in the Experiment-1 benchmark (BUILD_SEQUENCING.md).
    • Local-Path Composition — Recorded Decision (2026-07-12, Fool's NC-3): The tokenization bypass for local Ollama (above) composes with §12's endpoint posture: un-tokenized names, email addresses, and phone numbers flow to a localhost endpoint whose impersonation detection is best-effort (§12 error.ollama.port_hijack) — the local path is simultaneously the least-verified path and the one without the tokenization safety net. This is an accepted composition within §02's threat boundary: a same-user local process that can bind 127.0.0.1:11434 is the already-conceded same-user adversary. It is recorded here so it is a documented decision rather than an omission; revisit if §02's threat model tightens or if §12's endpoint verification becomes cryptographic rather than best-effort.
  • Telemetry: Emit context.block.injected (type, token_count, source_table, age_seconds) and context.block.withheld (type, reason, age_seconds, threshold_seconds). The refresh/disclosure path adds, in the same context.* family and under §16's payload rules (compact operational facts and non-secret identifiers only — never block content or user text): context.refresh.attempt (type, domain, lane, budget_ms), context.refresh.success (type, domain, duration_ms, age_seconds_after), context.refresh.timeout (type, domain, budget_ms, background_continued), context.refresh.failure (type, domain, error_category, background_continued), and context.absence.disclosed (type, domain, status, age_seconds, last_synced_at). 15Tool SystemComplete▶

Tools are startup-discovered YAML contracts with explicit mode eligibility and narrative templates that let artifact work acknowledge immediately, run in the background, and hand back results cleanly.

18Memory SystemComplete▶

memory_db separates durable personal truths from warm/cold memory entries, then exposes only fresh L2 memory summaries to the LLM.

  • Database: memory_db is SQLCipher encrypted and opened with WAL plus busy_timeout=5000.
  • Personal truths: personal_truths are runtime facts about this user, distinct from EDICTS rules and VOICE style; updates come from explicit user instruction or high-confidence Lilith inference.
  • Warm tier: tier='warm' for entries accessed within 30 days or accessed at least 3 times in the last 90 days; eligible for CWM recall after L2 summarization.
  • Cold tier: tier='cold' for older or low-access entries; retained in SQLCipher but deprioritized and only recalled for explicit memory searches or artifact work.
  • Consolidation: APScheduler daily cron at 03:20 local time moves warm entries to cold when last_accessed is older than 30 days and regenerates affected memory_l2_summaries.
  • CWM boundary: CWM injects personal_truths and memory_l2_summaries only; raw memory_entries bodies never enter provider payloads.
  • Recall mechanism (v6 v1 — single-developer practical implementation): Two-stage retrieval. Stage 1: recency — SELECT * FROM memory_entries WHERE tier='warm' ORDER BY last_accessed DESC LIMIT 20. Stage 2: FTS5 keyword relevance — SELECT * FROM memory_fts WHERE memory_fts MATCH :query ORDER BY rank LIMIT 10. Results merged, deduplicated, scored by recency + FTS5 rank, top entries passed to L2 for summary. FTS5 external-content table indexes heading || ' ' || body || ' ' || tags. Semantic/vector recall (local embeddings) is not in v6 v1 — its committed target architecture, promotion gate, and forward-compatibility requirements are the Recall Roadmap below, which replaces the previous unbounded "future phase" note. Cold entries only surface on explicit recall queries in artifact mode.
  • Recall Roadmap (staged hybrid retrieval — amended 2026-07-27, retrieval research review): Hybrid retrieval is the committed target for memory recall, adopted in stages so the conversational lane's felt speed is never spent on unproven retrieval infrastructure.
    • Named target architecture (v6.x, not v6 v1): Hybrid recall = existing FTS5/BM25 keyword search + dense vector search over locally-computed embeddings, merged via reciprocal rank fusion, feeding the same dedup/score/L2 path as v1. Brute-force KNN only — no ANN index infrastructure. At personal-memory scale (thousands to low hundreds-of-thousands of entries), measured brute-force latency is tens of milliseconds provided the dimension bound below holds; ANN adds maintenance surface without a latency need at this scale.
    • Embedding model class & dimension bound (normative): A small on-device embedding model (≤500M parameters, quantized, EmbeddingGemma-class) with stored vectors truncated to 256–384 dimensions (Matryoshka-style truncation). The dimension bound is normative, not advisory: brute-force KNN latency scales with dimension (measured: ~100K vectors at 1536 dims already costs ~100 ms; small dims keep the same scan in single-digit-to-tens of ms), and the bound is what makes no-ANN viable.
    • Lane-split adoption rule: The two lanes adopt hybrid separately. The artifact lane may adopt hybrid recall (and additionally cross-encoder reranking and multi-query decomposition over warm and cold tiers) as soon as the promotion gate passes — reranking and decomposition are slow-lane techniques by measurement (decomposition + rerank pipelines run ~19 s/query-class) and are never placed on the conversational path. The conversational lane adopts hybrid only if the measured end-to-end recall step (query embedding + brute-force KNN + RRF merge) fits inside the §14 staleness-refresh budget on target hardware with margin; until then the conversational lane keeps v1 recency + FTS5, which remains a fully supported configuration, not a degraded mode.
    • Promotion gate (Experiment 3, BUILD_SEQUENCING.md): No embedding dependency, vector extension, or sidecar table ships until Experiment 3 (Encrypted Vector Feasibility) passes on target hardware: the version-pinned vector extension (sqlite-vec-class — pre-v1 software; breaking-change risk is recorded and pinning is mandatory) must load into the project's SQLCipher build, and brute-force KNN at the bounded dimensions must meet the experiment's latency criteria. Compatibility of SQLCipher with vector extensions is treated as unproven until demonstrated in this project's build, not assumed from upstream documentation.
    • Forward compatibility (normative in v6 v1): Embeddings arrive additively as a model-versioned sidecar table inside memory_db — memory_embeddings(memory_id REFERENCES memory_entries(id), model_name, model_version, dims, vector BLOB, generated_at) — under the same SQLCipher encryption. Adopting or changing an embedding model shall never rewrite or migrate memory_entries; a model change means re-embedding sidecar rows (tracked by model_name/model_version), nothing else. v6 v1 code shall not preclude this table.
    • Design validation note (non-normative): The 2026-07-27 retrieval research review found the doc's existing write-time distillation (personal truths + L2 summaries, §17/§18) and precomputed-context-block pattern (§14) independently aligned with the strongest published results for conversation-derived memory — structured write-time memory outperforming raw chunk-and-embed retrieval, and background-computed context outperforming turn-time speculative retrieval at local scale. No speculative/prefetch retrieval machinery is warranted; the L1/L2 pipeline already occupies that role.
    • EARS requirements:
      • Where hybrid recall is active, the memory system shall merge FTS5 and vector candidate sets via reciprocal rank fusion before the existing dedup/score/L2 path, and shall retain FTS5 as a co-equal retriever (never vector-only).
      • The conversational lane shall not adopt vector recall until Experiment 3 has passed and the measured recall step fits the §14 conversational refresh budget on target hardware.
      • When the embedding model or version changes, the system shall re-embed memory_embeddings rows and shall not modify memory_entries.
      • When Experiment 3 has not passed, the system shall contain no vector-extension or embedding-model dependency.
    • Telemetry at adoption: memory.recall's stage enum extends with 'vector'; RRF-merged recalls emit one event per contributing stage. No new events in v6 v1.
  • Telemetry: Emit memory.write (tier, action, memory_id), memory.truth.update (key, source), and memory.recall (query_hash, results_returned, stage: 'recency'|'fts5').

27The OrbComplete▶

ModernGL 5.x UV sphere rendered in a PySide6 QOpenGLWidget at 60fps. Voice-reactive amplitude. Five-state state machine. Spring-physics position.

  • Rendering: moderngl.create_context() attaches to Qt's existing OpenGL context in initializeGL(). UV sphere: 48 sectors × 24 stacks, radius 0.18. Vertex layout: 6 floats per vertex (3f 3f = position + normal). Two GLSL shaders: lilith/ui/shaders/orb.vert (model matrix from position uniforms), lilith/ui/shaders/orb.frag (Fresnel glow effect). QTimer at 16ms (~60fps) drives update() → paintGL().
  • State machine: five states driven by UICommandBus.set_orb_state(state):
    • idle — gentle slow pulse, center position
    • listening — amplitude-reactive (VAD RMS input), slightly enlarged
    • processing — animated spin/shimmer, neutral size
    • speaking — amplitude-reactive (TTS RMS output), slightly enlarged
    • doing — contracted (smaller radius), moved toward UI area being modified
  • Position: spring-physics interpolation toward (target_x, target_y) in clip space. Step: pos += (target - pos) * 0.07 per frame. Call OrbWidget.set_target(x, y) from UICommandBus to move it.
  • Amplitude: OrbWidget.set_amplitude(rms: float) called from audio thread via Qt signal. Exponential smoothing: smooth_amp = smooth_amp * 0.82 + raw_amp * 0.18. Prevents popping on transients.
  • Uniforms: u_pos_x, u_pos_y, u_amplitude, u_time (increments 0.016/frame).
  • Public API: set_amplitude(value: float), set_target(x: float, y: float), set_state(state: str).

Amendment — Data Ownership
29Vault Architecture & Data OwnershipComplete▶

Lilith is a data custodian, not a warehouse. She does not duplicate or copy user documents, notes, or media files; instead, she reads them from their original locations and stores internal SQLCipher databases, telemetry, config, logs, and skills in a secure app directory (APP_INTERNAL_DIR).

  • Custodian Philosophy: Lilith operates on the principle that the user's data belongs strictly to the user. Rather than creating a proprietary repository or importing/copying files into an internal workspace, Lilith indexes files, documents, and other note vaults (such as Obsidian vaults) directly from where they live. Losing or uninstalling Lilith has zero impact on the user's original files — but it deletes Lilith's own accumulated history (memories, conversations, finance records, and indexes in the six internal databases) together with every internal backup of it, because both live under APP_INTERNAL_DIR (§06 Residency & Failure Domain). The custodian promise covers what the user brought to Lilith; the exported-backup discipline in Backups & Restore below is what protects what Lilith accumulated.
  • Portability without Lock-in: Lilith does not lock users in. Although her internal SQLCipher databases (contacts.db, calendar.db, finance.db, memory_db, conversation_db, ucl.db) are encrypted with a raw 256-bit AES key derived via Argon2id (which is not openable via typical passphrase prompts in standard database browsers), the user can derive the raw hex key from their master passphrase and salts.dat using the standalone key tool (lilith-key-tool) or the documented CLI commands.
  • Internal Storage Structure: All databases, salts, config, logs, models, and cache live inside APP_INTERNAL_DIR with 0700 directory and 0600 file permissions.
  • Note Vault Integration (Obsidian, etc.): Lilith parses and indexes external markdown note vaults (such as Obsidian vaults) in-place. She ingests, analyzes, and mutates content into her own layered internal representation, leaving the user's original vaults completely untouched and readable by external tools at all times.
  • Cloud Storage Integration (Drive/iCloud/OneDrive): Integration with third-party cloud drive platforms (Google Drive, iCloud, OneDrive) is explicitly deferred to v6.1+. In v6 v1, Lilith interacts strictly with local filesystem paths and pointers.
  • Backups & Restore (SEC-019): Built-in tools allow full backup and restore of all 6 internal databases and their key material (salts.dat) together as one atomic set (plus the non-secret backup.manifest.json, §06), making user histories portable across machines or OS reinstalls.
    • Export destination: The backup tool writes exported sets to a user-chosen path outside APP_INTERNAL_DIR — default ~/Documents/Lilith Backups/ (platform equivalents, permission rules, and layout in §04 EXTERNAL_BACKUP_DIR; a destination inside APP_INTERNAL_DIR is rejected). An optional setting additionally mirrors the §06 automated daily set to the same destination's automatic/ subfolder, with hash verification and never-silently-disabled failure handling per §06 Mirror Unavailability.
    • Uninstall & data-loss boundary (normative, honest): Uninstalling Lilith — or deleting APP_INTERNAL_DIR by any means — deletes the six internal databases and every internal backup of them in one operation. An exported backup set plus the master passphrase that was in effect when it was taken is the recovery unit; nothing else recovers accumulated history. Keychain entries survive uninstall but hold no data and cannot recover anything by themselves (§25 state row (f) handles that post-reinstall state).
    • Synced-folder note (honest implication): The user may point the destination at a folder synced by their own cloud service, and on Windows the default Documents folder may itself be OS-redirected into one (§04). An exported set contains the SQLCipher ciphertext plus the salts.dat needed to derive its keys, so possession of a set gives an attacker everything except the master passphrase — the passphrase is the only protection of an exported set (§02 threat model: backup leakage). The export UI states this plainly; it is not hidden in documentation. This introduces no cloud service on Lilith's side and does not change the §29 cloud-integration deferral.
    • Export reminders (lightweight): Two surfaces, neither gating: (1) Settings → Backups shows the last automated backup time, the last export/mirror time and mirror status (from config.json, §06), and a standing notice while no export has ever been made; (2) the end of first-run onboarding shows a one-time dismissible reminder (§25 Step 8) that data lives only on this machine until a backup is exported.
    • Restore: On a fresh install or after a reinstall, "Restore from a backup" is a first-class entry point in the §25 startup state machine (welcome screen and reinstall-detected row (f)): the set is completeness-checked against its manifest, staged, opened with the entered passphrase, integrity-checked, and only then placed — with failure paths (wrong passphrase, incomplete set, integrity failure) following §25's never-delete conventions, and the source set opened read-only throughout.
  • Skills Directory: The custom skill library lives in APP_INTERNAL_DIR/skills/. Shipped/curated skills stay frictionless because the installer includes a packaged skills.manifest.json containing each curated skill name, relative path, version, and SHA-256 hash. Startup indexing accepts curated skills whose bytes match that manifest, records them as trust_source=curated, and rejects or quarantines missing, modified, duplicate, malformed, or hash-mismatched entries before they can be parsed or injected.
  • Uncurated Skill Friction: Arbitrary third-party or self-authored skills remain possible but intentionally inconvenient. There is no GUI approve button. The user must place the file manually, run a CLI-only enrollment command such as lilith skills enroll APP_INTERNAL_DIR/skills/example/SKILL.md, review the displayed path, parsed metadata, warnings, and SHA-256 hash, then type both the exact hash and the phrase I accept unverified skill risk for this exact file. Enrollment writes the path and hash to skills.user-manifest.json; any byte change invalidates approval and requires repeating the process.
  • Skill Parsing & Injection Constraints: Skill frontmatter and manifests are parsed only with yaml.safe_load or strict JSON parsing as applicable. Approved skill content is injected only as a delimited, labeled context block under the EDICTS rule that skill text is never authoritative over EDICTS, privacy, memory-write gates, tool permissions, or user consent. Every injection emits router.skill.injected with skill name, SHA-256 hash, trust source, manifest status, and task id.
  • Skills Trust Boundary (honest, normative): The manifest/hash/CLI-friction layer above is a control against accidental enrollment, silent file corruption, and tampering by an attacker who cannot rewrite the manifests. It is not a control against a determined social engineer: an attacker who walks the user through the enrollment ritual (a skill pack shipping copy-paste enrollment instructions is the expected shape) gets their skill injected verbatim, and typing the hash and risk phrase proves the user performed the ceremony deliberately — it does not mean Lilith or anyone else vetted the skill, and enrollment must never be presented as vetting. It is also not a control against same-user malware: a process running as the user can rewrite skills.manifest.json, skills.user-manifest.json, and the SKILL.md files together, so startup hash verification passes against attacker-controlled reference hashes — the same same-user boundary §02's threat model already concedes for SQLCipher and the keychain. For an enrolled-but-hostile skill, the remaining runtime defenses are the §13 delimiter and EDICTS rule (which depend on model compliance and are exactly the indirect-prompt-injection boundary no current LLM holds reliably), the §13 injection size cap, the §26 answer-time untrusted-skill indicator, and the router.skill.injected audit trail. Claim ceiling (same rule as §02's privacy-copy ceiling): no product, onboarding, or marketing copy may present the skills integrity layer as protection against social engineering, malicious-but-enrolled skills, or same-user malware; user-facing copy may claim less than this paragraph states, never more.
  • Skill Size Cap at Enrollment & Verification (§13): lilith skills enroll rejects any SKILL.md whose raw file size exceeds SKILL_MAX_INJECTED_BYTES (§13: 8,192 bytes, a config.py working hypothesis) before hashing or parsing, printing the actual size, the cap, and the reason (injected skill bodies are context-budget-bounded: an oversized body crowds EDICTS and personal truths out of the smallest supported local-model context window and inflates every matched artifact-turn's cost). Startup manifest verification applies the same check to curated and user-enrolled entries: an over-cap file is quarantined with the same non-destructive handling as a hash mismatch and is never parsed or injected. The cap is enforced a third time at injection by the router (§13, router.skill.oversize), so a file that grows after enrollment fails closed even though any byte change already invalidates its hash approval. Over-cap files are rejected whole, never truncated — truncation can silently change a skill's meaning.
