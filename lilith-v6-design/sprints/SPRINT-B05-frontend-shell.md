## Goal

The pipeline gets a face. At sprint end, `python -m lilith.app` (on a bootstrapped machine) opens a PySide6 window instead of waiting in `signal.pause()`: a sidebar with the two M1 screens; a `"conversation"` screen whose transcript shows speech bubbles and tool-panel cards and whose typed input goes through `Conversation.respond` (the CH-03/CH-04 pipeline, persistence and PII tokenization intact); a ModernGL orb that idles and visibly pulses with live microphone amplitude; and a `"settings"` screen whose API key entry lands in the OS keyring and is used by the next LLM call. Every backend-originated UI change reaches the widgets only through the `UICommandBus`. No onboarding, contacts, calendar, skill-indicator or full orb state machine exists.

### Definition of Done (verbatim from `BUILD_GUIDE.md` §5, CH-05)

- [ ] GUI launches from the app entry point; typed input flows through the CH-03/CH-04 pipeline and renders as bubbles and tool panels.
- [ ] Orb renders, idles, and visibly reacts to live audio amplitude.
- [ ] API key entered in Settings lands in the OS keyring per §02 and is used on the next LLM call.
- [ ] UI events cross threads only via `UICommandBus`; no direct cross-thread widget calls (code-review check).

### [B05-02] `UICommandBus`: the thread-safe event bus
**Type:** [IMPLEMENT]
**Law:** `../sections/s26.html` (`UICommandBus:`, `Module dependency direction:`), `../sections/s27.html` (`State machine:`), `../sections/s28.html` (`Navigation:`), `../BUILD_SEQUENCING.md` §2.1 (§26 row: "thread-safe `UICommandBus` to dispatch events to the GUI"), `../sections/s08.html` (`UCL Telemetry Assertions:`, `Payload Schema Review:`)
**Depends on:** B05-01, BD-021

**What to build:**
- In `lilith/ui/bus.py` (the §01 tree's `bus.py`: "UICommandBus for thread-safe main thread updates"; the file is a docstring-only placeholder today) the class `UICommandBus(QObject)`. It lives on the main thread (§26: "a `QObject` subclass that lives on the main thread") and exposes the three `@Slot` methods shown in §26, with exactly these signatures: `set_orb_state(self, state: str)`, `append_message(self, json_payload: str)`, `show_screen(self, screen_name: str)`.
- The bus holds no widget logic of its own: each slot re-emits a typed Qt signal (or calls the one registered receiver) that the orb, the chat screen and the main window connect to, so that the bus is the only object the backend ever addresses (§26: "All UI mutations go through a UICommandBus that the backend calls — the UI never calls the backend directly"). The shape of that registration is the implementer's, recorded in the report; it adds no behaviour the section does not state.
- Cross-thread delivery follows §26: the backend calls "via `QMetaObject.invokeMethod(..., Qt.ConnectionType.QueuedConnection)`". The task writes the one place the backend side does this (the composition root's call site, B05-10), and a documented rule — in the module docstring and in `docs/` — that no other thread may call a bus slot or a widget method directly.
- Payload handling per BD-021: `append_message` parses its JSON with `json.loads`, validates the declared keys, and on an invalid payload rejects it without raising into the Qt event loop and without logging the payload text (a declared `ui.*`-style event is allowed only if BD-021/BD-027 name one inside the §16 `user.*` or `error.*` namespaces; otherwise the rejection is silent and tested).
- No `set_skill_indicator` slot (skills are EXCLUDED) and no slot for screens other than the two M1 screens' names.
- Unit tests (offscreen): each slot, when called from the main thread, delivers to a connected receiver; **when invoked from a worker `threading.Thread` through `QMetaObject.invokeMethod` with `QueuedConnection`, the receiver runs on the main thread** (the test records `QThread.currentThread()` in the receiver and asserts it is the application thread, with the event loop processed by the harness); several rapid calls from a worker arrive in order; an invalid JSON payload and an unknown screen or state name are handled per BD-021 and never raise into the loop.

**Docs:** `docs/CHANGELOG.md` `B05-02` entry. Create `docs/architecture/data-flows/ui-event-flow.md`: the bus, the three slots, the queued-invoke rule with a Mermaid sequence (backend thread → `invokeMethod` → main thread slot → receiver), the payload schema from BD-021, and the status line "bus built; receivers land in B05-03…B05-08". Update `docs/architecture/01-containers.md` only to name `ui/bus.py` as built.

**Acceptance criteria:** the three slots exist with the §26 signatures; the thread-affinity test proves a worker-thread queued invoke executes the receiver on the main thread; invalid payloads never raise into the event loop; `lilith/ui/bus.py` imports nothing from `lilith.logic`, `lilith.data` or `lilith.app`. Unit/full gates and Docs contributions pass.

### [B05-03] `OrbWidget` animation model: public API, smoothing, spring, states
**Type:** [IMPLEMENT]
**Law:** `../sections/s27.html` (`State machine:`, `Position:`, `Amplitude:`, `Uniforms:`, `Public API:`), `../BUILD_SEQUENCING.md` §2.1 (§27 row: "basic idle and voice-reactive pulsing. Advanced state migrations are deferred"), `../sections/s26.html` (`UICommandBus:`)

**What to build:**
