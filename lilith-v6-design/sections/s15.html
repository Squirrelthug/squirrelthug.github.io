Tools are startup-discovered YAML contracts with explicit mode eligibility and narrative templates that let artifact work acknowledge immediately, run in the background, and hand back results cleanly.

  • Definition format: lilith/tools/*.yaml, parsed with PyYAML==6.0.3, requiring name, description, JSON-schema-like parameters, mode, and narratives.
  • YAML safety rule: All tool contracts and skill frontmatter are untrusted input and MUST be parsed with yaml.safe_load only. yaml.load, yaml.full_load, custom YAML object constructors, or any parser mode that can instantiate Python objects are prohibited for lilith/tools/*.yaml, SKILL.md frontmatter, packaged manifests, and user-enrolled manifests. Skill files are additionally size-gated before parsing: a SKILL.md whose raw file size exceeds SKILL_MAX_INJECTED_BYTES (§13) is rejected at CLI enrollment and quarantined at startup manifest verification without ever reaching yaml.safe_load — the size check runs on raw bytes, ahead of any parser.
  • Data-status notice in the artifact lane (DS-0, 2026-11-01; AD-112): The machine-generated data-status marker (§14) is written for the model. Where no model sits between a tool and the screen (the artifact lane), the marker is rewritten into one plain sentence for the user (“Note: your calendar data is stale (last synced…), so this may be out of date.”); the model-facing text is unchanged.
  • Locality and who chooses a tool (design session DS-1, 2026-11-02): A tool contract may declare locality: local_only (the default) or cloud_ok. A local_only tool's result is shown to the user and is never sent to a cloud model: not in the same turn, and not as later conversation history. A cloud_ok result (reserved for tools such as the clock and calculator) may be returned to the model. The model may choose a tool and supply its arguments from the user's own message; the arguments are untrusted text, the app validates them and restores any PII tags locally, and the app, not the model, decides what runs. A per-answer user opt-in that lets the model read one local_only result is designed but not built.
  • Mode enum: conversational_only, artifact_only, or both; router rejects unavailable tools before any LLM call.
  • Narrative keys: acknowledge, bridge, handoff, and failure are mandatory for every artifact-capable tool.
  • Acknowledge: Artifact tools fire narratives.acknowledge to TTS within <200 ms after router classification.
  • Bridge: Default bridge interval is 8 s; v6 v1 uses static templates such as Still working on that..., with UCL-adaptive timing deferred.
  • Handoff: v6 v1 handoff is deterministic template fill from the typed tool result; PERS-2 narration is not in the first implementation.
  • Network tools and weather (design session DS-3, 2026-11-02): a tool may reach the network only through a platform client with a compiled-in host allowlist, https only, no redirects, no proxy from the environment, a response size cap and an injectable transport for tests. The first is weather (Open-Meteo, keyless; its free API is for non-commercial use and its data is CC BY 4.0, so each answer carries “Weather data by Open-Meteo.com”). Each lookup sends at most a place name to the geocoder and coordinates to the forecast service, nothing else. Code, not the model, geocodes, fetches and writes the sentence from the returned numbers. A network tool is off until the user’s own words turn it on (“turn on weather”, claimed by read dispatch and never offered to the model), the first ask shows what is sent and to whom, “turn off weather” reverses it, and both are recorded in the action ledger. The home city is a personal truth the user states (home_city, source user), never inferred. A lookup waits off the event-loop thread, from a snapshot of the settings. Telemetry: tool.network.request (provider, endpoint, outcome, duration_ms), logged ok only after the answer is accepted; never the place or the answer.
  • The contract network field (design session DS-3, 2026-11-02): a tool contract may declare network: true (a YAML boolean; absent means false; any other type is rejected). A contract that declares network: true must also declare locality explicitly: a network tool never relies on the local_only default. The set of shipped network tools is computed from the contracts (network_tools()), and it is the one list the capability panel and the chapter audit read to say which abilities contact the internet. weather is the first.
  • Opening apps from a user-curated allow-list (developer decision 2026-11-02, design session DS-3): Lilith may open an installed application only if the user has put it in the allow-list by dragging its icon (or pressing Allow) in Settings > Apps; that grant is the consent, and no launch asks again. The model-chosen app_open tool passes the app name in the user’s words; code resolves it against the allow-list only, and the model never sees the installed or allowed apps (app_open is local_only). A launch is argument-free and never uses a shell or an application’s own command line: Linux gtk-launch <desktop-id> (fallback gio launch on the enumerated file), macOS open -b <bundle-id>, fixed argv, the id validated by grammar, by a fresh enumeration and by the allow-list. A refusal repeats the spoken name and never reveals what is installed. The model has no tool that can grant, widen or edit the allow-list. Telemetry: apps.allowlist (action, count), apps.scan (count, supported), app.launch (outcome, and the app id only when the request resolved to exactly one allowed app).
  • Web search through the user’s own SearXNG (design session DS-3; provider decided by the developer 2026-11-02): web search goes only to a SearXNG instance the user runs on the same machine, at http://127.0.0.1:8888 (plain http is allowed only because the host is the loopback address; any other host is refused before a request is built). It is keyless and free. The request carries the query words and format=json and nothing else; SearXNG passes the words on to public engines, which see the words and the user’s internet address, never a name, calendar, contacts or notes. The web_search tool is model-chosen and local_only; it is off until the user’s own words turn it on (“turn on web search”), the first ask shows what is sent and to whom, and “turn off web search” and undo reverse it. Results are shown verbatim as a plain-text panel with the query echoed and “not checked” stated; a result’s text, title and link are never written to a database (the stored turn keeps only the “Searched for” line and a count). A setup kit (a compose file bound to loopback, a settings file with JSON on, and a script that writes them but never runs anything) helps the user start the service, and Lilith says plainly when it is not answering.
  • Deep search and the spider (design session DS-8, 2026-11-02): the deep_search tool (model-chosen, local_only, network: true, behind the web-search switch) runs one background job at a time: SearXNG finds up to five pages; the spider fetches each; the artifact lane reads them; a sourced report is shown and the pages are deleted. The spider fetches only URLs from the user’s search results or message, depth 0; http/https only; every address the host resolves to must be a global address, checked again on every redirect hop (at most 3), so a page cannot point it at the user’s own network; it obeys robots.txt, identifies itself, makes one request at a time per host with a delay, caps time and size, accepts only HTML and plain text, and never runs JavaScript. The report’s source list is built from the structured URLs, never from model text, and is shown as plain text marked “from the web, not checked”. While a job runs the user may ask how long it will take: the answer is computed from measured progress and, only then and only with an Anthropic key, says that “go faster” would use the cloud at a cost. “Stop the research” cancels and purges.
  • Telemetry: Emit tool.call.start (tool_name, mode), tool.call.complete (duration_ms, success), tool.narrative.ack (tool_name), and tool.narrative.handoff (tool_name, artifact_id).
