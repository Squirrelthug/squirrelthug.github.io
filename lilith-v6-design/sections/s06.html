Infrastructure Layer
06Process Lifecycle & RecoveryComplete▶

Lilith manages single-instance execution via a PID lockfile, operates a strictly ordered 10-phase startup sequence, and recovers from prior crashes via non-destructive, consensual backup restoration and quarantine.

  • Single-Instance Lock: Stored at APP_INTERNAL_DIR/lilith.lock. On boot, the app opens this file and attempts to acquire an exclusive OS-level lock (using fcntl.flock on POSIX, msvcrt.locking on Windows). Lock acquisition success is the sole authoritative source of truth that no other instance is running. If lock acquisition fails, the application displays a dialog stating "Lilith is already running" and exits immediately. When lock acquisition fails, the system reads the stored PID from the lock file and checks if a process with that PID exists and matches the application name (via psutil) only to enrich the user-facing dialog message, never to gate or decide the startup refusal itself, avoiding false-positive blocks due to post-crash PID reuse.
  • Ten-Phase Startup Sequence (Launch to Audio Ready):
    1. Phase 1 (Hardware Profile): Detect VRAM/RAM, assign capability tier (stored in-memory).
    2. Phase 2 (Process Lock): Acquire lilith.lock, write current process PID. Verify 0700/0600 folder and file permissions.
    3. Phase 3 (Keyring Verification): Verify secure OS keyring backend availability.
    4. Phase 4 (Salt Loading): Load salts.dat from APP_INTERNAL_DIR/databases/salts.dat. If databases exist but salts.dat is missing, halt startup with a recovery error screen ("Salts missing — restore salts.dat from backup to recover access"). If salts.dat is absent and no database files exist either, Phase 4 generates nothing: the run proceeds to the §25 classification (first run, reinstall-detected row (f), or restore-from-backup) with the directory state untouched. Salts are created via os.urandom(192) only inside onboarding's clean-install path (§25 Step 5), arrive as part of a restored backup set (§25 restore flow), or are regenerated by the passphrase-change flow (§02/§03) as fresh salts staged and swapped inside the rotation journal's committed batch — never eagerly during startup phases, where premature generation would manufacture local key material and mask the reinstall-detected state (§02's no-database-files rule scopes to startup/onboarding classification and is not violated by rotation's staged regeneration; SEC-025).
    5. Phase 5 (Unlock Mode Resolution): Run the §25 prompt-compatible startup detection. Convenience mode reads master_passphrase from keychain; prompt mode asks the user to type it; missing master_passphrase with existing databases is credential recovery, not first-run onboarding.
    6. Phase 6 (Database Mounting): Derive keys via Argon2id. Connect to all 6 SQLCipher databases (located at APP_INTERNAL_DIR/databases/), run PRAGMA key and verify with a dummy query. If keying fails, halt and prompt for passphrase re-entry; never delete the databases.
    7. Phase 7 (Database Migrations): Execute idempotent migration scripts in a transaction. Take an automated pre-migration backup before starting.
    8. Phase 8 (Scheduler Launch): Initialize APScheduler and register background cleanup/sync jobs.
    9. Phase 9 (Voice Pipeline Init): Load Whisper and Kokoro model files; open Sounddevice Streams.
    10. Phase 10 (Application Active): Render PySide6 window, play a short welcome chime, and transition Orb to idle.
  • Graceful Shutdown Sequence:
    1. Stop mic capture stream immediately (close Sounddevice inputs).
    2. Shut down the APScheduler scheduler (scheduler.shutdown(wait=True) to allow active jobs to exit).
    3. Abort any in-flight LLM HTTP queries.
    4. Close all database connections (flushing WAL journal logs).
    5. Release and delete lilith.lock.
    6. Exit process (status 0).
  • Automated Backups (SEC-011):
    • Trigger & Schedule: Automated backups are taken daily (via a background job scheduled at 03:20) and immediately prior to running database migrations (Phase 7).
    • Set Composition: Backups are atomic packages containing all 6 databases + the matching salts.dat + a non-secret backup.manifest.json (set format version, creation timestamp in UTC, app version, and per-file name/size/SHA-256 — never passphrases, keys, or other key material), stored in a timestamped folder under APP_INTERNAL_DIR/backups/backup-<timestamp>/. The manifest is what makes completeness and copy integrity mechanically checkable at mirror and restore time (§25 restore-from-backup flow). Manual exports via the §29 backup tool produce the identical set format.
    • Verification: Immediately after creation, Lilith performs PRAGMA integrity_check on all backed-up database files. If any checks fail, the backup is deleted and error.backup.verify_failed is logged as a critical error.
    • Retention: Lilith retains the 7 most recent valid backup sets, deleting older ones automatically. The same 7-set retention applies independently to mirrored sets under EXTERNAL_BACKUP_DIR/automatic/ — Lilith prunes only sets there that match her naming and manifest format. Manual exports at the destination root are never auto-deleted.
    • Residency & Failure Domain (SEC-019): Internal sets under APP_INTERNAL_DIR/backups/ share one failure domain with the primary databases: uninstall, disk failure, or deletion of the app directory destroys the store and every internal backup of it in a single operation. Internal sets are therefore the fast recovery path for corruption and rotation rollback (state row (c), §25; §02 rotation preflight) — they are not durable protection. Durable protection is an exported or mirrored set at EXTERNAL_BACKUP_DIR (§04); §29 defines the recovery unit (exported set + the master passphrase in effect when it was taken).
    • External Mirror (optional setting, SEC-019): When Settings → Backups → "Also keep backups outside Lilith" is enabled (off by default; surfaced by the §29 export reminders), each successful automated backup is additionally copied to EXTERNAL_BACKUP_DIR/automatic/ and verified by re-hashing every copied file against the set's backup.manifest.json. A mirrored set that fails hash verification is deleted from the destination and the copy is treated as a mirror failure; the verified internal set is unaffected.
    • Mirror Unavailability (normative): The internal backup is never gated on the mirror: it is created and verified first, and succeeds or fails on its own regardless of the external destination's state. If the destination is unavailable or the copy/verification fails (unmounted drive, deleted folder, permission error, full disk), Lilith logs error.backup.mirror_failed (reason code), surfaces a non-blocking notice in Settings → Backups, and retries at the next scheduled backup. After 3 consecutive mirror failures the notice becomes a persistent warning that remains until a mirror succeeds or the user disables the setting. Mirroring is never silently disabled, and a mirror failure never blocks, delays, or aborts the internal backup.
    • Backup UCL events (error.* namespace, §16): error.backup.verify_failed, error.backup.mirror_failed (reason), error.backup.export_failed (reason). Payloads carry set id, trigger (daily|pre_migration|pre_rotation|manual_export), location class (internal|external), sizes, durations, and reason codes only — never key material (§16 sanitizer gate). Successful backup/mirror/export timestamps are recorded in config.json for the Settings → Backups panel (§29) rather than as new UCL namespaces.
  • Crash Recovery & Consensual Restore (SEC-004 / SEC-011): At startup, if the lockfile exists but the PID inside is dead, a crash is assumed and Lilith cleans the lock. Startup then branches based on the state of the databases, salts, and onboarding marker (see state table in §25).
    • State Machine Gating: Startup distinguishes between setup crashes (a), key failures (b), and structural database corruption (c). In case of keying failure (b), databases are never touched or deleted, and the user is directed to the salts/passphrase recovery path.
    • No Silent Restoration: If structural corruption is detected (c) on one or more databases, Lilith does NOT silently restore or overwrite files. She presents a recovery screen offering per-database restoration from the latest valid atomic backup set (containing all 6 databases + matching salts.dat), showing the backup timestamp and data-loss interval.
    • Quarantine by Default: Prior to any destructive clean restart or database restore, the affected files (partial databases, salts, or corrupt databases) are moved to a quarantine folder (APP_INTERNAL_DIR/databases/quarantine-<timestamp>/) rather than being deleted outright.
    • Recovery Logs: Every recovery action, including corruption detections, quarantine moves, clean setup restarts, and restorations, is logged as an error.recovery.* UCL telemetry event (e.g., error.recovery.onboarding_crash, error.recovery.corruption_detected, error.recovery.quarantine_created, error.recovery.database_restored).
    • Restore Entry Point (fresh install / reinstall, SEC-019): The corruption recovery above restores from internal sets on a machine that still has a live store. Recovering onto a machine with no local store — new machine, OS reinstall, post-uninstall — is a different flow: the §25 restore-from-backup entry point, reachable from the first-run welcome screen and from the reinstall-detected state row (f), which verifies and places an exported set from EXTERNAL_BACKUP_DIR or any copy of one.
  • APScheduler Lifecycle: Instantiated and started in Phase 8 (right after migrations). Closed as the first step of graceful shutdown.
  • Passphrase Rotation Journal & Crash Resume (SEC-009):
    • Journal: The passphrase-change flow (§02) maintains APP_INTERNAL_DIR/databases/rotation.journal — a small non-secret JSON file recording the staging directory name, per-database staging progress, and the current phase (verify → preflight → stage → commit → finalize), written with atomic write-then-rename and fsync at each phase transition. It never contains passphrases, salts, keys, or PRAGMA text.
    • Commit point: Writing phase commit to the journal is the point of no return. Before that write, the live databases and salts.dat are untouched and the staged files are disposable. After it, the staged files are authoritative and the swap proceeds by renames: all old files (6 databases + salts.dat) move to databases/quarantine-rotation-<timestamp>/, then all staged files (including the staged salts.dat) move into place as one batch.
    • Startup resolution (Phase 4 pre-step): Before loading salts.dat, Phase 4 checks for rotation.journal. This check precedes every other state classification (including the missing-salts halt), because a mid-swap crash can legitimately leave salts.dat in transit. If the journal phase is earlier than commit: roll back — delete the staging directory and the journal; the live store is untouched and the user is told: "A passphrase change didn't finish. Nothing was changed — your previous passphrase is still in effect." If the journal phase is commit or later: roll forward — complete any remaining renames (each rename is idempotent and resumable from the journal's per-file record), prompt the user for the new passphrase, verify it opens all six databases, then in convenience mode write it to the keychain (the final step, per §02), delete the journal, and continue startup. The verified passphrase is handed to Phase 5 in memory so the user is not prompted twice. Both outcomes are deterministic; see the §25 state-table rows (d) and (e). If rotation.journal is present but unreadable or unparseable (disk-level corruption of the journal itself — unlikely given its atomic write-then-rename discipline, but reachable), neither branch applies: startup routes to the §25 explicit recovery screen — never auto-rollback, never auto-resume, never delete — with the journal, the staging directory, and any quarantine contents preserved untouched for manual recovery (SEC-028).
    • Cleanup: After a successful finalize, the old-key files in quarantine-rotation-<timestamp>/ are deleted — the preflight backup set (under the old passphrase) remains the restore point and ages out via normal retention.
    • UCL events (security.rekey.*, §16): security.rekey.start, security.rekey.backup_created, security.rekey.export_complete (db_name), security.rekey.commit, security.rekey.keychain_updated (convenience mode only), security.rekey.complete, security.rekey.rolled_back, security.rekey.resumed. Payloads carry phase, database name, and durations only — never key material (§16 sanitizer gate, §03 exception boundary). While connections are closed during the swap window no UCL events can be written; the journal is the authoritative record for that window and event logging resumes after reopen.
  • Backups Across Rotation (SEC-009): Each backup set is self-contained (6 databases + the matching salts.dat) and remains encrypted under whichever master passphrase was in effect when it was taken; retained sets are never re-keyed retroactively. Restoring a pre-rotation set is supported: the restore flow warns "This backup was taken before your last passphrase change — enter the passphrase that was in use when it was taken," verifies that passphrase against the set before restoring, and restores the set's own salts.dat with it; the store then operates under that older passphrase, and in convenience mode the restore commit writes the verified older passphrase back to the keychain so the keychain and databases never disagree. The rotation flow pauses the daily backup job for its duration (no backup can capture a mid-rotation state) and takes a fresh post-rotation backup at finalize, so the newest retained set always matches the current passphrase. Retention (7 most recent valid sets) is unchanged by rotation.
