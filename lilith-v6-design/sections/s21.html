Application Layer
21Finance AppComplete▶

finance_db stores encrypted transaction and account data. Import is deterministic (no LLM parsing). Categorization is rules-based in v6 v1.

Database schema (finance_db — SQLCipher encrypted):

accounts(
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  institution TEXT,
  type        TEXT CHECK(type IN ('checking','savings','credit','investment')),
  currency    TEXT DEFAULT 'USD',
  created_at  REAL NOT NULL
)

transactions(
  id              TEXT PRIMARY KEY,
  account_id      TEXT REFERENCES accounts(id),
  date            REAL NOT NULL,
  amount          REAL NOT NULL,          -- positive = credit, negative = debit
  merchant        TEXT,
  category        TEXT,                   -- see category list below
  description     TEXT,
  import_source   TEXT,                   -- 'pdf', 'csv', 'manual'
  import_batch_id TEXT,                   -- groups rows from one import run
  raw_source_fingerprint TEXT,            -- stable hash of source row/page/statement identity
  dedup_status   TEXT DEFAULT 'clear' CHECK(dedup_status IN ('clear','candidate','confirmed_duplicate','confirmed_distinct')),
  dedup_group_id TEXT,                    -- groups ambiguous duplicate candidates for review
  created_at      REAL NOT NULL
)
  • Import — PDF: pdfplumber remains deterministic, but v6 v1 does not claim universal PDF adaptivity. PDF import is a named adapter pipeline per institution and statement family. Supported v6 v1 adapters are: Chime Checking statements, Chime Savings statements, Chime Credit Builder/Credit statements, Cash App Account statements, and Cash App Savings statements. Each adapter owns its institution detection, page/table extraction, sign convention, date parsing, multiline-description handling, and corpus fixtures. Additional banks are unsupported until real sample statements are collected and a bank-specific adapter is added.
  • Import — CSV: header keyword matching for column mapping. Handles any export with date + amount + description columns.
  • Auto-categorization: keyword rules applied to merchant field at import time. Nine categories: Housing, Food, Transport, Healthcare, Entertainment, Shopping, Utilities, Income, Other. Rules live in data/finance/categories.yaml — editable without code changes.
  • Unsupported PDF behavior: When a dropped-in PDF does not match a supported adapter signature, Lilith rejects PDF import for that file with a clear unsupported-bank message, records no transaction rows from that PDF, and offers CSV/manual import or "add bank adapter" guidance. Unsupported PDFs are never silently parsed through a generic best-guess table mapper.
  • L1: duplicate detection job — exact source fingerprints may be treated as already-imported rows, but same date + amount + merchant within a 24h window is only a duplicate candidate. Before flagging, the job checks stronger disambiguating signals when present: source transaction id/reference, timestamp precision beyond calendar date, posted/settled date pair, running balance/net amount continuity, statement line index/page identity, account id, import batch id, and normalized raw row fingerprint. If the available signals cannot prove the rows are the same source transaction, both rows are preserved and grouped with dedup_status='candidate' for user review. The job never silently discards an ambiguous finance transaction.
  • L2: spending summaries by category and period. Produced by template (not LLM) in v6 v1. LLM reads this output only.
  • Tools: finance_summary(period: str, category: str | None) → str — returns narrative spending summary. spending_trend(periods: int) → str — compares N periods against prior N. Both artifact_only mode.
  • UCL events: tool.call.start, tool.call.complete (from §15). Import-specific: sync.finance.import_complete (batch_id, row_count, duplicate_candidate_count, auto_deduped_exact_count) and sync.finance.unsupported_bank_pdf (institution_hint, filename_hash, reason).

EARS requirements — PDF import scope:

  • Where PDF import is active, the finance importer shall route each PDF through an explicit supported-bank adapter selected by institution and statement-family signature.
  • When a Chime Checking, Chime Savings, Chime Credit Builder/Credit, Cash App Account, or Cash App Savings statement is imported, the matching adapter shall parse transaction rows using that statement family's mapped layout, sign convention, date fields, and multiline-description rules.
  • When a PDF does not match a supported adapter signature, the finance importer shall stop before row creation and show a clear unsupported-bank message.
  • When a new institution is added, the system shall require real sample statements and adapter-specific fixtures before the institution is listed as supported.

EARS requirements — duplicate handling:

  • When an imported row has the same raw source fingerprint as an existing row for the same account, the deduplication job shall treat it as an exact previously imported source row.
  • When two rows share date, amount, and normalized merchant within 24 hours, the deduplication job shall compare stronger disambiguating signals before deciding whether the rows are the same transaction.
  • When stronger disambiguating signals prove two rows are different legitimate transactions, the deduplication job shall preserve both rows as clear transactions.
  • When stronger disambiguating signals are missing or inconclusive, the deduplication job shall preserve both rows and flag the pair or group for user review.
  • The deduplication job shall not discard a same-day, same-amount, same-merchant row solely because it resembles another row.

Acceptance criteria:

  • Given a supported Chime or Cash App statement PDF, when the user imports it, then Lilith selects the matching bank adapter, parses the statement without LLM parsing, creates the expected transaction rows, and emits sync.finance.import_complete.
  • Given a PDF statement from an unlisted bank, when the user drops it into finance import, then Lilith shows an unsupported-bank message, creates no transaction rows from that PDF, and offers CSV/manual import or adapter-addition guidance.
  • Given a statement contains two same-day, same-amount, same-merchant purchases, when no timestamp, source id, running balance, or other stronger signal proves they are the same transaction, then Lilith preserves both rows and flags them for user review instead of discarding either row.

Future/conditional: Plaid-style bank linking is worth investigating after v6 v1 only if it is genuinely free or low-cost for a small independent developer and does not require a large-institution partnership. It is not a v6 v1 requirement and is excluded from the acceptance criteria above.
