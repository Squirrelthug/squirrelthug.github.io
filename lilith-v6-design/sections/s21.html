Application Layer
21Calendar AppComplete▶

calendar_db holds two strictly separated event stores: a read-only, provenance-tagged mirror of the user's Google Calendar kept fresh by the §19 sync, and Lilith's own writable calendar — the system ingests the user's calendar and keeps its own calendar up to date; it can write to its own calendar, but the user's calendar is safe from this untested system. More telemetry is required before Lilith is ever granted the ability to manage the user's own calendar. The full working spec is specs/calendar-app.spec.md; this section is the law derived from it.

Database schema (calendar_db — SQLCipher encrypted):

synced_events(                            -- read-only mirror of the user's Google Calendar
  id            TEXT PRIMARY KEY,         -- Google event id
  ical_uid      TEXT,                     -- iCalendar UID as delivered by Google
  calendar_id   TEXT NOT NULL,
  summary       TEXT,
  description   TEXT,
  location      TEXT,
  start_ts      REAL,
  end_ts        REAL,
  all_day       INTEGER DEFAULT 0,
  status        TEXT,                     -- confirmed/tentative/cancelled, as synced
  etag          TEXT,
  synced_at     REAL NOT NULL,
  provenance    TEXT NOT NULL DEFAULT 'google_sync',
  echo_of_lilith_event_id TEXT REFERENCES lilith_events(id)  -- set only by the L1 echo job; NULL = genuine user event
)

lilith_events(                            -- Lilith's own calendar: events she creates for the user
  id          TEXT PRIMARY KEY,
  ical_uid    TEXT NOT NULL UNIQUE,       -- RFC 5545 UID, stable for the event's lifetime
  summary     TEXT NOT NULL,
  description TEXT,
  location    TEXT,
  start_ts    REAL NOT NULL,
  end_ts      REAL NOT NULL,
  all_day     INTEGER DEFAULT 0,
  status      TEXT NOT NULL DEFAULT 'confirmed' CHECK(status IN ('confirmed','tentative','cancelled')),
  sequence    INTEGER NOT NULL DEFAULT 0, -- RFC 5545 SEQUENCE; incremented on every update/cancel
  created_at  REAL NOT NULL,
  updated_at  REAL NOT NULL
)

Google Calendar API (§19, read-only) -> synced_events mirror ─┐
                                                               ├─ L1: echo tag + conflict flag -> L2 period agenda -> artifact tools/CWM
lilith_events (Lilith-owned, writable) ────────────────────────┘
        └─> ICS subscription feed (read-only, token path, Lilith events only)
  • Database: calendar_db uses SQLCipher with WAL and busy_timeout=5000; all event PII is encrypted at rest (§03).
  • Google mapping (§19 sync, machinery unchanged): event id -> id, iCalUID -> ical_uid, summary/description/location -> same-named columns, start/end -> start_ts/end_ts (+all_day), status -> status, etag -> etag, sync time -> synced_at. The mirror exists to be overwritten by the next sync — the user keeps changing their own calendar and Lilith always stays current.
  • Mirror integrity: the §19 sync is the only writer of Google-sourced fields in synced_events; no tool, UI action, or L2 job mutates the mirror. The sole non-sync writer is the L1 echo-detection job, which sets only the local annotation column echo_of_lilith_event_id.
  • Lilith's calendar: events Lilith creates for the user live in lilith_events, modeled as a standards-compliant calendar (iCalendar UID, SEQUENCE, STATUS semantics). Create sets a fresh UID and sequence=0; every update or cancel increments sequence so feed subscribers observe the change. Cancel, never hard-delete: status='cancelled', row retained.
  • Tools: reads agenda(period: str) -> str and event_lookup(query: str) -> str follow the §20 pattern — artifact_only, returning L2-style text, never raw rows. Writes calendar_event_create, calendar_event_update, calendar_event_cancel operate on lilith_events ONLY and refuse mirrored-event ids with an explicit message. All tools emit tool.call.start/tool.call.complete (§15).
  • ICS subscription feed (the keystone): Lilith's calendar is published as a read-only ICS feed so the user can subscribe from their own calendar client if they choose. Most users will hopefully depend on Lilith to convey and organize their tasks throughout the day; some of those users also want a glance at the view they have always used — the information is identical either way, and the design services that user: Lilith knows what the user knows AND the user stays informed in the way they have always been informed. The feed contains ONLY Lilith-originated events (mirrored Google events are never republished); it is served locally (loopback by default, LAN opt-in) at an unguessable token path /calendar/<token>/lilith.ics (secrets.token_urlsafe(32), stored inside calendar_db, never logged, regenerable — regeneration invalidates the old URL). GET only; wrong token → 404, non-GET → 405. Cancelled events are published with STATUS:CANCELLED and their incremented SEQUENCE.
  • Honest limitation (LAN feed): device-polling clients on the same network (e.g., Apple Calendar) can subscribe in v6 v1. Google Calendar polls from Google's servers and cannot reach a LAN feed — remote feed publishing is deferred, consistent with §29's cloud deferral. The token path is capability-style security on the local network, not authentication: anyone on the LAN who learns the URL can read Lilith's calendar. User-facing copy states both limitations plainly; it may claim less than this paragraph, never more.
  • L1 — echo detection (mandatory) + conflict flagging: if the user subscribes to Lilith's feed in a calendar that syncs back through §19, Lilith's events return as Google events. After each sync, the L1 job matches incoming synced events' iCal UIDs against lilith_events.ical_uid and tags matches as echoes (echo_of_lilith_event_id); echoes are excluded from agenda merging and conflict detection — each event appears exactly once and never conflicts with itself. Separately, a genuine (non-echo) user event overlapping an active Lilith event is flagged for user review — never auto-resolved, moved, or cancelled. The job is idempotent and re-run safe.
  • L2 — merge at view/summary time only: no storage-layer merge of the two stores. The L2 job produces period agenda summaries by template (non-LLM, per §17's untrusted-domain rule), merging non-echo mirror events with active Lilith events at summary time; CWM reads L2 only. The calendar domain's refresh_capability remains sync_and_enhance (§17) — the refresh machinery needs no changes. §19's address-context preprocessing (raw location → relative plain-text) applies to both stores before CWM ingestion.
  • Telemetry: existing events unchanged: sync.calendar.* (§19), tool.call.start/tool.call.complete (§15). New: sync.calendar.echo_detected (lilith_event_id, google_event_id), calendar.conflict.flagged (lilith_event_id, synced_event_id, overlap_minutes), calendar.feed.served (event_count, response_bytes) — payloads per §16 hygiene, never event content.

EARS requirements — store separation and write scope:

  • The calendar application shall maintain synced_events and lilith_events as two separate stores with no storage-layer merge.
  • When a §19 calendar sync runs, the sync pipeline shall be the only writer of Google-sourced fields in synced_events.
  • Where LLM-callable calendar write tools are active, the tools shall create, update, or cancel rows in lilith_events only.
  • When a write tool receives an event id that does not identify a lilith_events row — including any mirrored Google event id — the tool shall refuse the operation, modify no row, and return an explicit refusal message.
  • When calendar_event_cancel succeeds, the system shall set status='cancelled' and increment sequence, and shall never hard-delete the row.
  • When calendar_event_update succeeds, the system shall increment sequence so feed subscribers observe the change.
  • The system shall not register, request, or expose any Google Calendar write operation in v6 v1: no write scope is requested, no write-back method is registered, and no tool definition exposes a Google Calendar mutation — reaffirming §19's read-only enforcement.

EARS requirements — ICS feed:

  • Where the ICS feed is enabled, the system shall serve Lilith-originated events only and shall never serialize mirrored Google events into the feed.
  • The feed server shall accept only HTTP GET at the token path, shall respond 404 to an unknown path or wrong token without disclosing valid paths, and shall respond 405 to any non-GET method.
  • The feed server shall bind to loopback by default and, where LAN serving is enabled, to the local network interface only.
  • When an event is updated or cancelled, the feed shall publish its current SEQUENCE and STATUS (including STATUS:CANCELLED).
  • The feed server shall serialize and respond within 2 seconds for calendars of up to 5,000 Lilith events.

EARS requirements — echo detection and conflicts:

  • When a calendar sync completes, the L1 job shall compare each incoming synced event's iCalendar UID against lilith_events.ical_uid and set echo_of_lilith_event_id on every match.
  • While a synced event carries echo_of_lilith_event_id, the L1 and L2 jobs shall exclude it from agenda merging and conflict detection, so each event appears exactly once and never conflicts with itself.
  • When a non-echo synced event overlaps in time with an active Lilith event, the L1 job shall flag the pair for user review and shall never auto-resolve, move, or cancel either event.

Acceptance criteria:

  • Given the user asks Lilith to schedule an event, when calendar_event_create completes, then a lilith_events row exists with a fresh UID and sequence 0, the ICS feed includes the event, no Google API write call was issued, and the user's Google Calendar is unchanged.
  • Given the user has subscribed to Lilith's feed in a calendar that syncs back through §19, when the next sync imports an echoed copy whose iCal UID matches a lilith_events row, then the L1 job tags it as an echo, emits sync.calendar.echo_detected, the agenda shows the event exactly once, and no conflict is flagged between the event and its echo.
  • Given a mirrored Google event id, when any calendar write tool is invoked with it, then the tool refuses with an explicit message and no row in either store is modified.
  • Given an active Lilith event with sequence N, when calendar_event_cancel runs, then the row remains with status='cancelled' and sequence N+1, and the feed publishes STATUS:CANCELLED.
  • Given a genuine (non-echo) user event overlapping an active Lilith event, when the L1 job runs, then the pair is flagged for review, calendar.conflict.flagged is emitted, and neither event is modified.
  • Given the v6 v1 tool registry and OAuth configuration, when audited, then no Google Calendar write scope is requested, no write-back method is registered, and no tool exposes a Google Calendar mutation.

Future/conditional: Remote feed publishing (which would let Google Calendar's servers subscribe) is deferred, consistent with §29's cloud deferral. Additional ingest sources (ICS/CalDAV/Apple Calendar) are deferred — Google Calendar is the sole ingest source in v6 v1. Granting Lilith the ability to manage the user's own calendar is gated on accumulated telemetry demonstrating reliable behavior of Lilith's own calendar, and requires a future documented design session; it is excluded from the acceptance criteria above.
