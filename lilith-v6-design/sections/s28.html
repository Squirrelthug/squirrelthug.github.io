Frontend Layer
28Screen Architecture & NavigationComplete▶

Five named screens in a QStackedWidget. The Orb floats above the stack and persists across all screens. Navigation is always initiated via UICommandBus, never directly between screens.

MainWindow layout:
┌─────────────────────────────────────────┐
│  OrbWidget (QOpenGLWidget, floating)    │
├────────┬────────────────────────────────┤
│ Side-  │  QStackedWidget                │
│  bar   │  ┌──────────────────────────┐  │
│  nav   │  │ conversation (default)   │  │
│        │  │ contacts                 │  │
│        │  │ calendar                 │  │
│        │  │ settings                 │  │
│        │  │ onboarding (first-run)   │  │
│        │  └──────────────────────────┘  │
└────────┴────────────────────────────────┘
  • Screen names (string identifiers): "conversation" (default after onboarding), "contacts", "calendar", "settings", "onboarding" (only during first-run flow).
  • Navigation: UICommandBus.show_screen(name: str) calls QStackedWidget.setCurrentWidget(). Sidebar nav buttons call UICommandBus — they do not call the stack directly.
  • Orb behavior by screen:
    • conversation — orb center-top, state driven by voice pipeline
    • contacts / calendar — orb contracted (doing state), positioned near the active UI region
    • settings — orb idle, corner position
    • onboarding — orb center, large, speaking state during Lilith's intro
  • Screen implementations: each screen is a QWidget subclass in lilith/ui/screens/. Screens do not communicate with each other — all inter-screen data flows through UICommandBus or the backend.
  • Sidebar: fixed-width icon + label nav. Active screen item highlighted. Hidden during onboarding flow.
  • UCL events: user.screen.navigate (from_screen, to_screen) on every navigation
