Amendment — Data Ownership
29Vault Architecture & Data OwnershipComplete▶

Lilith is a data custodian, not a warehouse. She does not duplicate or copy user documents, notes, or media files; instead, she reads them from their original locations and stores internal SQLCipher databases, telemetry, config, logs, and skills in a secure app directory (APP_INTERNAL_DIR).

  • Custodian Philosophy: Lilith operates on the principle that the user's data belongs strictly to the user. Rather than creating a proprietary repository or importing/copying files into an internal workspace, Lilith indexes files, documents, and other note vaults (such as Obsidian vaults) directly from where they live. Losing or uninstalling Lilith has zero impact on the user's original files — but it deletes Lilith's own accumulated history (memories, conversations, finance records, and indexes in the six internal databases) together with every internal backup of it, because both live under APP_INTERNAL_DIR (§06 Residency & Failure Domain). The custodian promise covers what the user brought to Lilith; the exported-backup discipline in Backups & Restore below is what protects what Lilith accumulated.
  • Portability without Lock-in: Lilith does not lock users in. Although her internal SQLCipher databases (contacts.db, calendar.db, finance.db, memory_db, conversation_db, ucl.db) are encrypted with a raw 256-bit AES key derived via Argon2id (which is not openable via typical passphrase prompts in standard database browsers), the user can derive the raw hex key from their master passphrase and salts.dat using the standalone key tool (lilith-key-tool) or the documented CLI commands.
  • Internal Storage Structure: All databases, salts, config, logs, models, and cache live inside APP_INTERNAL_DIR with 0700 directory and 0600 file permissions.
  • Note Vault Integration (Obsidian, etc.): Lilith parses and indexes external markdown note vaults (such as Obsidian vaults) in-place. She ingests, analyzes, and mutates content into her own layered internal representation, leaving the user's original vaults completely untouched and readable by external tools at all times.
  • Cloud Storage Integration (Drive/iCloud/OneDrive): Integration with third-party cloud drive platforms (Google Drive, iCloud, OneDrive) is explicitly deferred to v6.1+. In v6 v1, Lilith interacts strictly with local filesystem paths and pointers.
  • Backups & Restore (SEC-019): Built-in tools allow full backup and restore of all 6 internal databases and their key material (salts.dat) together as one atomic set (plus the non-secret backup.manifest.json, §06), making user histories portable across machines or OS reinstalls.
    • Export destination: The backup tool writes exported sets to a user-chosen path outside APP_INTERNAL_DIR — default ~/Documents/Lilith Backups/ (platform equivalents, permission rules, and layout in §04 EXTERNAL_BACKUP_DIR; a destination inside APP_INTERNAL_DIR is rejected). An optional setting additionally mirrors the §06 automated daily set to the same destination's automatic/ subfolder, with hash verification and never-silently-disabled failure handling per §06 Mirror Unavailability.
    • Uninstall & data-loss boundary (normative, honest): Uninstalling Lilith — or deleting APP_INTERNAL_DIR by any means — deletes the six internal databases and every internal backup of them in one operation. An exported backup set plus the master passphrase that was in effect when it was taken is the recovery unit; nothing else recovers accumulated history. Keychain entries survive uninstall but hold no data and cannot recover anything by themselves (§25 state row (f) handles that post-reinstall state).
    • Synced-folder note (honest implication): The user may point the destination at a folder synced by their own cloud service, and on Windows the default Documents folder may itself be OS-redirected into one (§04). An exported set contains the SQLCipher ciphertext plus the salts.dat needed to derive its keys, so possession of a set gives an attacker everything except the master passphrase — the passphrase is the only protection of an exported set (§02 threat model: backup leakage). The export UI states this plainly; it is not hidden in documentation. This introduces no cloud service on Lilith's side and does not change the §29 cloud-integration deferral.
    • Export reminders (lightweight): Two surfaces, neither gating: (1) Settings → Backups shows the last automated backup time, the last export/mirror time and mirror status (from config.json, §06), and a standing notice while no export has ever been made; (2) the end of first-run onboarding shows a one-time dismissible reminder (§25 Step 8) that data lives only on this machine until a backup is exported.
    • Restore: On a fresh install or after a reinstall, "Restore from a backup" is a first-class entry point in the §25 startup state machine (welcome screen and reinstall-detected row (f)): the set is completeness-checked against its manifest, staged, opened with the entered passphrase, integrity-checked, and only then placed — with failure paths (wrong passphrase, incomplete set, integrity failure) following §25's never-delete conventions, and the source set opened read-only throughout.
  • Skills Directory: The custom skill library lives in APP_INTERNAL_DIR/skills/. Shipped/curated skills stay frictionless because the installer includes a packaged skills.manifest.json containing each curated skill name, relative path, version, and SHA-256 hash. Startup indexing accepts curated skills whose bytes match that manifest, records them as trust_source=curated, and rejects or quarantines missing, modified, duplicate, malformed, or hash-mismatched entries before they can be parsed or injected.
  • Uncurated Skill Friction: Arbitrary third-party or self-authored skills remain possible but intentionally inconvenient. There is no GUI approve button. The user must place the file manually, run a CLI-only enrollment command such as lilith skills enroll APP_INTERNAL_DIR/skills/example/SKILL.md, review the displayed path, parsed metadata, warnings, and SHA-256 hash, then type both the exact hash and the phrase I accept unverified skill risk for this exact file. Enrollment writes the path and hash to skills.user-manifest.json; any byte change invalidates approval and requires repeating the process.
  • Skill Parsing & Injection Constraints: Skill frontmatter and manifests are parsed only with yaml.safe_load or strict JSON parsing as applicable. Approved skill content is injected only as a delimited, labeled context block under the EDICTS rule that skill text is never authoritative over EDICTS, privacy, memory-write gates, tool permissions, or user consent. Every injection emits router.skill.injected with skill name, SHA-256 hash, trust source, manifest status, and task id.
  • Skills Trust Boundary (honest, normative): The manifest/hash/CLI-friction layer above is a control against accidental enrollment, silent file corruption, and tampering by an attacker who cannot rewrite the manifests. It is not a control against a determined social engineer: an attacker who walks the user through the enrollment ritual (a skill pack shipping copy-paste enrollment instructions is the expected shape) gets their skill injected verbatim, and typing the hash and risk phrase proves the user performed the ceremony deliberately — it does not mean Lilith or anyone else vetted the skill, and enrollment must never be presented as vetting. It is also not a control against same-user malware: a process running as the user can rewrite skills.manifest.json, skills.user-manifest.json, and the SKILL.md files together, so startup hash verification passes against attacker-controlled reference hashes — the same same-user boundary §02's threat model already concedes for SQLCipher and the keychain. For an enrolled-but-hostile skill, the remaining runtime defenses are the §13 delimiter and EDICTS rule (which depend on model compliance and are exactly the indirect-prompt-injection boundary no current LLM holds reliably), the §13 injection size cap, the §26 answer-time untrusted-skill indicator, and the router.skill.injected audit trail. Claim ceiling (same rule as §02's privacy-copy ceiling): no product, onboarding, or marketing copy may present the skills integrity layer as protection against social engineering, malicious-but-enrolled skills, or same-user malware; user-facing copy may claim less than this paragraph states, never more.
  • Skill Size Cap at Enrollment & Verification (§13): lilith skills enroll rejects any SKILL.md whose raw file size exceeds SKILL_MAX_INJECTED_BYTES (§13: 8,192 bytes, a config.py working hypothesis) before hashing or parsing, printing the actual size, the cap, and the reason (injected skill bodies are context-budget-bounded: an oversized body crowds EDICTS and personal truths out of the smallest supported local-model context window and inflates every matched artifact-turn's cost). Startup manifest verification applies the same check to curated and user-enrolled entries: an over-cap file is quarantined with the same non-destructive handling as a hash mismatch and is never parsed or injected. The cap is enforced a third time at injection by the router (§13, router.skill.oversize), so a file that grows after enrollment fails closed even though any byte change already invalidates its hash approval. Over-cap files are rejected whole, never truncated — truncation can silently change a skill's meaning.
APP_INTERNAL_DIR/            ← hidden, operational/internal storage (POSIX 0700/0600)
├── config.json
├── lilith.lock
├── databases/
│   ├── salts.dat            ← database key salts (MUST travel with databases)
│   ├── ucl.db
│   ├── calendar.db
│   ├── contacts.db
│   ├── finance.db
│   ├── memory.db
│   └── conversation.db
├── backups/
│   └── backup-<timestamp>/  → atomic set: databases + salts.dat + backup.manifest.json
│                              (internal only — deleted with APP_INTERNAL_DIR on uninstall;
│                               durable copies live at EXTERNAL_BACKUP_DIR, §04)
├── skills/                  ← curated and deliberately user-enrolled skills
│   ├── skills.manifest.json
│   ├── skills.user-manifest.json
│   └── (SKILL.md files, safe-loaded, hash-pinned, and delimited on injection)
├── logs/
├── models/
└── cache/
