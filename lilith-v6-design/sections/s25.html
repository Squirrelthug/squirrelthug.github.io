First-run is detected from database/key-material existence plus non-secret onboarding sentinels, never from master_passphrase presence alone, so convenience mode and prompt mode share the same recovery-safe startup path.

Startup detection:
install_sentinel = python-keyring.get_password("com.squirrelthug.lilith", "install_sentinel")
security_tier = python-keyring.get_password("com.squirrelthug.lilith", "security_tier")  # convenience|prompt
keyring_pass = python-keyring.get_password("com.squirrelthug.lilith", "master_passphrase")  # convenience only
dbs_exist = all_databases_exist(APP_INTERNAL_DIR / "databases")
salts_exist = (APP_INTERNAL_DIR / "databases" / "salts.dat").exists()
onboarding_marker = onboarding_complete_marker_exists(APP_INTERNAL_DIR)
rotation_journal = (APP_INTERNAL_DIR / "databases" / "rotation.journal").exists()
keychain_evidence = any of install_sentinel, security_tier, keyring_pass present  # keychain entries survive uninstall on all three platforms
local_data = any file exists under APP_INTERNAL_DIR / "databases"  # DBs, salts.dat, staging or quarantine leftovers
→ rotation_journal: interrupted passphrase rotation → resolve per §06 rotation journal BEFORE any classification below (pre-commit: roll back, passphrase unchanged; post-commit: roll forward, prompt for NEW passphrase)
→ not keychain_evidence and not local_data and not onboarding_marker: first run → onboarding screen (welcome offers "Restore from a backup" alongside setup — see restore-from-backup flow)
→ keychain_evidence and not local_data and not onboarding_marker: reinstall detected → offer restore-from-backup or start fresh (state row (f), SEC-023)
→ install_sentinel and dbs_exist and salts_exist and security_tier == "convenience" and keyring_pass is not None: derive keys → DB open → main UI
→ install_sentinel and dbs_exist and salts_exist and security_tier == "prompt": prompt for passphrase → derive keys → DB open → main UI
→ install_sentinel and dbs_exist and salts_exist and security_tier == "convenience" and keyring_pass is None: credential missing → ask user to enter passphrase and choose restore convenience storage or switch to prompt mode
→ dbs_exist and not salts_exist: missing key material → halt; never delete DBs
→ partial DB/salt/onboarding state mismatch: setup interruption or path problem → explicit recovery screen; never delete without confirmation
→ KeyringError: show "keychain unavailable" error, exit
  • First-run detection: Query non-secret keychain state (install_sentinel, security_tier) and verify APP_INTERNAL_DIR/databases/, salts.dat, and the local onboarding completion marker. Onboarding starts only when all durable install evidence is absent. The presence or absence of master_passphrase is never the first-run flag.
  • Onboarding steps (in order):
    1. Welcome screen — Lilith introduces herself via TTS (af_bella voice, first audio within 500ms). The screen offers two first-class actions: continue with setup (Steps 2–8 below) or "Restore from a backup" (enters the restore-from-backup flow defined below — for users migrating machines or recovering after an OS reinstall).
    2. Name collection — user speaks or types their name. Stored as personal truth: key="name"
    3. Passphrase creation — typed, not spoken. Requires a minimum of 12 characters, a second matching confirmation entry, a static unmissable warning that losing the passphrase results in permanent data loss, and a strength check that rejects trivially weak patterns/common passphrases.
    4. Security tier selection — both tiers are presented side by side as first-class choices with symmetric copy (see tier-presentation requirements below): convenience (preselected default on all platforms) stores master_passphrase in the OS keychain for auto-unlock (as defined in §02's canonical credentials table); prompt stores no passphrase and requires typed unlock at every launch. On Linux, this step additionally displays the static keyring-exposure warning defined below — the same unmissable pattern as Step 3's no-recovery warning.
    5. Key derivation → DB creation (all 6 DBs in APP_INTERNAL_DIR/databases/) → salts generation (if clean install) → first migration run
    6. API key collection — user pastes Anthropic key. Tested with a live call before acceptance. Stored in keychain under key anthropic_api_key.
    7. Google auth (optional, skippable) — opens system browser for OAuth flow and stores only the offline refresh token.
    8. Onboarding complete → write install_sentinel and security_tier non-secret keychain entries → emit onboarding.complete UCL event and local completion marker → normal main UI, showing a one-time dismissible backup reminder (§29 export reminders): "Your memories and history live only on this machine. You can export a backup anytime in Settings → Backups." The reminder is informational only — it never gates completion or requires an action.
  • Functional Requirements (EARS Format):
    • When the user is on the passphrase creation screen, the system shall display an unmissable static warning: "There is no recovery — losing this passphrase permanently loses access to your data."
    • When the user submits a passphrase during onboarding, the system shall require a second matching confirmation entry before key derivation.
    • When the user enters a passphrase, the system shall reject the input if it fails a strength check or matches a blocklist of trivially weak common passphrases (e.g. repeating patterns, common dictionary words, or low score on a complexity estimator).
    • While onboarding is running on Linux, when the security tier selection step (Step 4) renders, the system shall display a static, plain-language warning stating that convenience mode stores the master passphrase in the system keyring where any program running as the same user can read it (the Freedesktop Secret Service API provides no per-application access control), and that prompt mode does not store the passphrase. Reference wording (normative content, final phrasing may be edited for tone without removing any of the three facts): "On Linux, convenience mode saves your master passphrase in the system keyring. Any program running as your user can read it — Linux has no per-app lock on the keyring. Prompt mode never saves it; you type it each time Lilith starts."
    • The system shall render the Linux keyring-exposure warning as static screen content that is visible without any user interaction — never behind a tooltip, hover state, expandable element, scroll fold, or documentation link.
    • When the security tier selection step renders on any platform, the system shall present both tiers with equal visual prominence and symmetric copy that states, for each tier: (a) what it protects against (convenience: powered-off/stolen-disk/copied-file scenarios per §02's threat model; prompt: additionally avoids persisting the master passphrase in the keychain), and (b) what it costs at startup (convenience: none, hands-free auto-unlock; prompt: typing the passphrase at every launch). Neither tier's copy may use subordinating framing (e.g. "advanced", "for experts", "not recommended"), and selecting prompt mode shall require no more interactions than selecting convenience mode. This defines normative content requirements, not final marketing text.
  • Acceptance Criteria (Given/When/Then):
    • AC-OB-001 (Passphrase Match): Given the user is on Step 3 of onboarding, when the user enters mismatched passphrases in the creation and confirmation inputs, then the system disables the "Next" action and displays a mismatch warning.
    • AC-OB-002 (Weak Passphrase): Given the user enters matching inputs, when the passphrase is weak or blocklisted, then the system blocks progress and displays a weak passphrase warning.
    • AC-OB-003 (Static Warning): Given the user is on the Step 3 screen, when the screen renders, then the warning of permanent data loss is prominently and statically visible in the UI.
    • AC-OB-004 (Linux Keyring Warning): Given onboarding is running on Linux, when the Step 4 tier-selection screen renders, then a static warning is visible without hover, click, expansion, or scrolling, stating that in convenience mode any program running as the same user can read the master passphrase from the system keyring and that prompt mode does not store it.
    • AC-OB-005 (Warning Platform Scoping): Given onboarding is running on macOS or Windows, when the Step 4 screen renders, then the Linux-specific keyring warning is not displayed, while the symmetric tier copy of AC-OB-006 is still displayed.
    • AC-OB-006 (Symmetric Tier Presentation): Given the user is on Step 4 on any platform, when the screen renders, then both tiers are visible with equal visual prominence, each stating what it protects against and what it costs at startup, and prompt mode can be selected directly on the screen with no more interactions than convenience mode.
    • AC-OB-007 (Warning Does Not Gate): Given onboarding is running on Linux with convenience mode preselected, when the user proceeds from Step 4 without changing the selection, then the system continues with convenience mode without any additional confirmation dialog — the warning informs the choice but does not block it.
  • Restore-from-Backup Flow (SEC-019): Entry points: the first-run welcome screen (Step 1) and the reinstall-detected state row (f). Restoring a set means placing the set's 6 databases + salts.dat into APP_INTERNAL_DIR/databases/ after verification, then proceeding per the chosen security tier. The flow, in order:
    1. Select: The user picks a backup set folder — an exported or mirrored set (typically under the §04 external backup destination) or any copy of one (USB drive, synced folder). The set's creation timestamp from backup.manifest.json is shown before anything else happens ("Restore the backup from <timestamp>?"). The source set is opened read-only and is never modified or deleted by this flow, in any outcome.
    2. Completeness check: The set is validated against its backup.manifest.json (§06 set composition): all files present, sizes and SHA-256 hashes match. A set without a manifest (pre-manifest era) is validated structurally instead: the 6 named databases + a 192-byte salts.dat. An incomplete or hash-mismatched set is refused with the missing or failing files named, and the user may pick another set.
    3. Stage: The set is copied to APP_INTERNAL_DIR/databases/restore-staging-<timestamp>/; all verification below runs against the staged copy, never against the source set.
    4. Passphrase verification: The user types the master passphrase that was in effect when the set was taken (§06 Backups Across Rotation: sets are never re-keyed, and the UI states this for sets that predate a passphrase change). Keys are derived from the staged salts.dat per §03 and verified against all six staged databases, then PRAGMA integrity_check runs on each. Wrong passphrase: re-prompt (no attempt limit), with the option to pick a different set; nothing is deleted. Integrity failure: the set is refused, the failing database(s) are named, and the user may pick another set; the staging copy is removed (it is Lilith's own copy — the source set is untouched).
    5. Place: Only after all six staged databases verify does the staged content move into APP_INTERNAL_DIR/databases/ as one batch. If any files already exist there (partial state), they are moved to databases/quarantine-<timestamp>/ first — never overwritten in place, never deleted (existing §06/§25 conventions).
    6. Tier & keychain: The user selects a security tier on the Step 4 screen (same requirements, including the Linux keyring-exposure warning and symmetric presentation). In convenience mode the verified passphrase is written to the keychain only now — after the restored store has been placed, opened, and verified (§02 keychain-write-last rule). install_sentinel, security_tier, and the local onboarding completion marker are then written. onboarding.complete is not emitted; the flow emits error.recovery.restore_complete instead.
    7. Credentials are not in backups: Backup sets contain only the 6 databases + salts.dat + manifest — never keychain credentials (§02 canonical table). After a restore on a fresh machine, Lilith prompts for the Anthropic API key (as in onboarding Step 6) and offers Google auth (Step 7); both are skippable there and re-enterable later in Settings.
    UCL events: error.recovery.restore_started, error.recovery.restore_complete (set timestamp), error.recovery.restore_failed (reason: wrong_passphrase | incomplete_set | integrity_fail | aborted). Payloads carry reason codes, set timestamps, and durations only — never passphrases, salts, or key material (§16 sanitizer gate).
  • Crash recovery & Prior-install detection:
    • Normal Startup: install_sentinel present AND all 6 DB files exist AND salts.dat exists at APP_INTERNAL_DIR/databases/salts.dat. Convenience mode reads master_passphrase from keychain; prompt mode asks the user to type it.
    • Credential Missing (Prompt-Compatible): Databases and salts.dat exist, security_tier is convenience, but master_passphrase is absent. Lilith treats this as missing credential state, not first run. It prompts for the passphrase, verifies all six databases, then lets the user restore convenience storage or continue in prompt mode.
    • State Machine-Gated Crash Recovery (SEC-004): Startup sequence routing is governed by a strict state table to distinguish setup crashes, credential issues, key/salts failures, and database-level corruption, preventing silent data destruction.
