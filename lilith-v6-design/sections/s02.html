02Security & Credential ManagementComplete▶

Credentials are managed through the OS keychain using python-keyring in convenience mode, or entered at launch in prompt mode, with strict startup safety checks that disable insecure fallbacks and a separate file for database salts to enable robust offline restores.

  • Keychain Service Name: "com.squirrelthug.lilith" (the unique namespace string used for all OS keyring queries).
  • OS-Specific Keyring Backends:
    • Linux Desktop: SecretServiceKeyring (Freedesktop Secret Service API via D-Bus).
    • macOS: macOS Keychain (Generic Password item class, secGenericPassword).
    • Windows: WinVaultKeyring (Windows Credential Manager encrypted via DPAPI).
  • Keychain Security Verification: Startup checks verify that keyring.get_keyring() returns a secure backend. If an insecure plaintext fallback (like keyrings.alt) or a failed keyring (FailKeyring) is detected, the app refuses to boot and raises an unrecoverable security exception.
  • Stored Credentials List & Key Names (Canonical Table):

    All secrets are managed under the unified service namespace "com.squirrelthug.lilith". In-memory access tokens are never persisted.

  • Salt File: Stored at APP_INTERNAL_DIR/databases/salts.dat. Format is exactly 192 bytes binary, consisting of six contiguous 32-byte cryptographically secure random salts (one for each of the 6 databases: ucl_db, calendar_db, contacts_db, finance_db, memory_db, conversation_db in fixed index order). Loaded via pathlib.Path.read_bytes(). It has exactly three legitimate origins (SEC-025): it is generated via os.urandom(192) inside onboarding's clean-install path (§25 Step 5) and only when no database files exist — never eagerly during startup classification (§06 Phase 4), where premature generation would mask the §25 reinstall-detected state; it arrives as part of a restored backup set (§25 restore-from-backup flow); or it is regenerated by the passphrase-change flow (the Stage step of the Passphrase Change & Key Rotation flow below / §03 Key Rotation Mechanics), where fresh salts are staged and swapped only as part of the §06 rotation journal's committed batch. The "only when no database files exist" rule scopes to startup/onboarding classification — it exists to protect the reinstall-detected state and does not forbid rotation's staged salt regeneration, which never generates salts outside a committed rotation batch. If databases exist but the salt file is missing, startup halts with a recovery error.
  • Security Tier Setting (v6 v1): Lilith ships two unlock modes. Convenience mode is the default and stores master_passphrase in the OS keychain so startup can auto-unlock. Prompt mode is available during onboarding and in settings; it never persists master_passphrase in the keychain, requires the user to type the passphrase at each app launch, and keeps derived database keys in process memory only until explicit relock or app exit. Switching from convenience mode to prompt mode deletes the persisted master_passphrase keychain item after verifying the typed passphrase can open all six databases. The keychain may still contain non-secret state such as install_sentinel and security_tier; these values do not unlock data. Recorded decision — default tier (2026-07-12, accepted risk): Convenience mode remains the default on all three platforms, including Linux, where the Secret Service caveat in the threat model below means any same-user process can read master_passphrase over D-Bus. Hands-free voice startup is the product's identity, and the threat model already concedes the same-user adversary. A platform-aware default (prompt mode as the Linux default) was considered and declined for v6 v1. This acceptance is conditional on §25's tier-selection step displaying the static Linux keyring-exposure warning and presenting both tiers with equal discoverability (AC-OB-004 through AC-OB-007); revisit this decision if dogfooding or user reports show the warning is insufficient.
  • Keyring Failure Recovery: If the keyring is unavailable or returns errors on startup, Lilith halts and displays a clear error screen: "OS secure keychain is unavailable. Please verify your system's keyring daemon is running."
  • Data Hygiene (SEC-018, Normative): Raw database rows never leave the device. Before cloud dispatch, the §14 tokenizer replaces person names, email addresses, and phone numbers in the compiled context with anonymous tags on a best-effort basis (rule-based detection; recall is not guaranteed, particularly for unusual names, nicknames, possessives, and names inside quoted message text). All other L2/context content — including merchant names and monetary amounts, health and relationship details, free-text notes, and location text outside §19's deterministic calendar-address preprocessing — is not detected and is sent as-is to the user's own BYOK provider over TLS, and never to any Lilith-operated service. Privacy-copy ceiling rule (Normative): any onboarding, marketing, or privacy copy describing this behavior must be derived from this paragraph as amended — the design document is the ceiling for user-facing privacy claims, never the floor; copy may claim less than this paragraph states, never more. No keyring operations are logged to prevent timing/leak vulnerabilities.
  • Directory & File Permissions (POSIX/Windows): All directories in APP_INTERNAL_DIR are created with strict 0700 permissions (directories) and 0600 (files) on POSIX. On Windows, per-user profile ACLs are set via DPAPI and NTFS permissions. Startup checks verify and enforce these permissions.
  • Threat Model & Security Boundary: SQLCipher encryption at rest protects user data from offline/at-rest attackers (e.g., physical media theft, disk exfiltration, backup leakage, or copied database files without the passphrase). It does not protect against a compromised active user session, same-user local malware, debugger access, process memory compromise, or a malicious process that can drive the unlocked app. On Linux, the Freedesktop Secret Service API has no per-application ACL, so any process in the same user session may be able to request keychain items over D-Bus; macOS and Windows provide stronger app/user binding but same-user malware remains outside the encryption-at-rest boundary. Convenience mode therefore protects powered-off/stolen/copy-only scenarios, not an already-compromised login session. Prompt mode reduces persistent keychain exposure but still cannot protect data once the passphrase has been entered and Lilith is unlocked.
  • Passphrase Change & Key Rotation (SEC-009, Normative): The master passphrase is changed only through the guarded passphrase-change flow, a rare foreground operation available in Settings in both security tiers. It runs with a progress UI and may take minutes; data safety strictly dominates speed. The flow is, in order:
    1. Verify: The user types the current passphrase — required in both tiers; the keychain value is never accepted as proof of user intent. Keys are derived per §03 and verified against all six databases before anything else happens.
    2. Collect: The user types the new passphrase twice, subject to the same minimum-length, confirmation-match, and strength/blocklist rules as onboarding Step 3 (§25).
    3. Preflight: Free disk space of at least the combined size of all six databases plus a 20% margin is confirmed; scheduled jobs (including the §06 daily backup) are paused; a fresh integrity-checked backup set is taken under the current passphrase as the guaranteed restore point.
    4. Stage: Six new 32-byte salts are generated — salts are always regenerated on rotation — new per-database keys are derived per §03, and each database is exported via sqlcipher_export() into a staged copy under the new key and integrity-checked (see §03 Key Rotation Mechanics). The live files are untouched during staging.
    5. Commit: All database connections are closed and the staged databases plus the staged salts.dat replace the live files as one committed batch under the crash-resumable rotation journal defined in §06.
    6. Finalize: Databases are reopened and verified under the new keys through a freshly constructed SessionKeyManager; only then — and in convenience mode only — is the keychain master_passphrase entry updated. The keychain write is always the final step of a completed database re-key; there is no code path that updates the keychain entry without a completed re-key. A fresh post-rotation backup is then taken immediately.
    Every step emits security.rekey.* UCL events (§06 lists the event set, §16 defines the namespace) whose payloads carry phase, database name, and durations only — never passphrases, salts, key material, or PRAGMA text (§03's keying exception boundary and §16's sanitizer gate apply). If the flow is interrupted at any point, the §06 rotation journal guarantees deterministic rollback or roll-forward at next startup.
  • Master Passphrase Write Path (Normative): Settings has no direct write control over master_passphrase. The only writers of that keychain entry are onboarding (§25 Step 3/4) and the final step of the passphrase-change flow above. Implementations must not provide any settings field, API, or code path that updates the keychain master_passphrase entry independently of a completed database re-key — a keychain-only passphrase change guarantees lockout (keychain holds the new passphrase while the databases remain keyed under the old one).
  • Credential Update & Revocation (Settings): All non-master secrets in the canonical table (anthropic_api_key, openai_api_key, ollama_bearer_token, google_oauth_refresh_token) are plain keychain values with no database-key coupling. Settings updates them by direct overwrite (keyring.set_password, taking effect on next use) and revokes them by deletion (keyring.delete_password plus invalidation of any in-memory client holding the old value; Google revocation additionally calls the provider's token-revocation endpoint on a best-effort basis). These simple keychain writes are explicitly distinct from the master-passphrase path above, which is never a simple keychain write. Non-secret entries (install_sentinel, security_tier) follow their existing §25/§02 writers.
  • Explicit Re-Lock (Normative): "Relock" means: all database connections are closed (WAL flushed), the SessionKeyManager and every derived key are dropped from process memory via SessionKeyManager.relock() (§03), scheduler jobs requiring database access are paused, voice capture stops, and the UI returns to a locked screen. A manual "Lock Lilith" action in Settings and the tray menu triggers relock in both tiers; relock and the subsequent unlock emit security.relock / security.unlock UCL events. Resuming from the locked screen: prompt mode requires the typed passphrase; convenience mode offers one-click unlock via the keychain (manual relock in convenience mode guards against casual physical access, not same-user malware — see Threat Model above). Recorded decision — idle-timeout auto-relock (2026-07-12): deferred beyond v6 v1. Lilith is a voice-first, always-listening assistant with scheduled background jobs (e.g. the 03:20 backup); an idle auto-relock would silently break wake-word response and scheduled work. It is recorded as a future opt-in for prompt mode, not a v1 requirement.
  • What Rotation Does — and Does Not — Do: Rotating the passphrase re-keys the live store, protects all future backups, and revokes the forward usefulness of a leaked keychain value or captured passphrase. It does not re-protect data already exfiltrated: any backup set (databases + salts) copied off the device under the old passphrase remains decryptable with that old passphrase forever. After a suspected compromise, rotation limits future exposure; it cannot recall the past. The flow takes a fresh backup automatically at finalize; retained older sets are not re-keyed and age out under §06's 7-set retention policy (see §06 Backups Across Rotation).
