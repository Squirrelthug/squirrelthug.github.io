Application Layer
22Conversation / Chat AppComplete▶

Every message is tagged with an endpoint — response format and capabilities are determined by the endpoint, not by the content.

Database schemas (conversation_db — SQLCipher encrypted):

sessions(
  id          TEXT PRIMARY KEY,
  started_at  REAL NOT NULL,
  ended_at    REAL,                -- NULL = session still open
  endpoint_id TEXT NOT NULL,
  turn_count  INTEGER DEFAULT 0
)

turns(
  id            TEXT PRIMARY KEY,
  session_id    TEXT REFERENCES sessions(id),
  role          TEXT CHECK(role IN ('user','assistant')),
  text          TEXT NOT NULL,
  timestamp     REAL NOT NULL,
  endpoint_id   TEXT NOT NULL,
  endpoint_type TEXT NOT NULL,
  mode          TEXT CHECK(mode IN ('conversational','artifact')),
  token_count   INTEGER
)
  • Endpoint types:
    • desktop — full artifacts OK, markdown rendered, no token cap
    • kitchen_speaker (deferred, future) — voice-only, ≤150 tokens, no markdown, no artifacts. Integrates with the "zero clearance, candid decline" model when implemented.
    • mobile (future) — voice + text, artifacts deferred to desktop hub
  • Response format rules: router checks endpoint.capabilities before generating. kitchen_speaker receives a stripped plain-text response regardless of artifact mode — artifacts are queued for desktop delivery.
  • Desktop text mode: The desktop chat screen is always available regardless of which endpoint lane the user is viewing. It includes a standard typed input composer, sends typed submissions through the same router and CWM policy as voice turns, records them as ordinary conversation turns, and returns the assistant response as text in the chat UI. Typed chat does not force TTS playback.
  • TTS on demand: Every assistant message rendered in desktop chat exposes a per-message speaker/play control. When the user activates that control, Lilith speaks that message through the configured TTS voice and records the playback request separately from the original assistant turn. Highlighted text inside an assistant message exposes the same speak-selection affordance, speaking only the selected text. Automatic voice playback remains a voice-surface behavior; desktop text mode is opt-in for TTS.
  • Endpoint Isolation Architecture: To prevent data crossover and leakage, each endpoint operates as a fully isolated communication lane.
    • Session Scoping: Every session in the database is strictly bound to a single endpoint_id. Sessions cannot span or continue across multiple endpoints, avoiding shared "active context" bleed.
    • Context and Notification Isolation: Dynamic context blocks (L1/L2) are built exclusively from the active session's parameters. Notifications and outbound payloads are sent only to the initiating endpoint; a message on one endpoint never triggers alerts or notifications on another.
    • Centralized Desktop Chat: The sole exception is the desktop chat screen, which offers a centralized, side-by-side view of each distinct lane (rendered per conversation/endpoint) rather than a merged single timeline.
  • Endpoint Authorization Tiers: Endpoints are categorized by identity verification:
    • Identity-Bound: Endpoints with reliable identity signals (e.g., Discord username) can be configured to filter and respond only to an authorized user identity, ignoring all other requests.
    • Zero-Clearance Ambient: Ambient/no-login devices (e.g., future kitchen_speaker) are granted zero security clearance. Sensitive queries involving finances, contacts, or personal memories are candidly declined over voice ("I cannot access that information without authentication") and redirect the user to an authenticated app surface.
  • Session lifecycle: session created on first turn. Session closed after 30 minutes of silence (APScheduler periodic check). A new turn after closure creates a new session.
  • Chat screen rendering: QListView with virtualized delegate. Conversational turn → speech bubble (left-aligned, minimal). Artifact response → panel card (full width, tool name header, timestamp, expandable content). Pending response → inline latency bridge tied to the active turn. Source tag on each item: endpoint type + timestamp.
  • Cross-device indicator: (Obsoleted by endpoint isolation) Because sessions cannot continue across different endpoints, this indicator is no longer used for session continuation; the desktop chat screen instead uses endpoint tags to label separate lanes in its centralized view.
  • UCL events: user.query.received (endpoint_id, endpoint_type, input_modality), user.query.classified (mode), tts.playback.requested (turn_id, scope, char_count), logged per turn.
  • Endpoint-Authorization Policy Home (SEC-024 / Fool's NC-5, Normative — ADR-013): The frozen database schema's endpoint_id in the sessions and turns tables is sufficient to scope history and enforce isolation. There is deliberately no schema table for endpoint configurations, authorized user identities, or clearance settings, because v6 v1 ships only the local desktop endpoint (deferred kitchen_speaker is zero-clearance ambient, needing no stored identity). Decision (v6 v1): endpoint-authorization policy — endpoint configurations, authorized identities, and clearance settings — lives in the file-based config.json. This is recorded as an explicit accepted risk within §02's same-user threat boundary: config.json sits under APP_INTERNAL_DIR with 0700/0600 permissions and carries no secrets (all secrets stay in the keychain per §02), and the same-user local adversary who could read or rewrite it is already conceded by §02's threat model, so plaintext policy adds no exposure v1 does not already accept. Binding migration trigger (normative, not a vague "future migration"): before any identity-bound endpoint (e.g., Discord — §22 Endpoint Authorization Tiers) is implemented, this policy MUST move out of config.json into an encrypted SQLCipher database with every authorization change written through the UCL (§16) as an auditable event. Identity-bound authorization is a security decision whose integrity and audit trail a plaintext file cannot provide; implementing such an endpoint while its policy still lives in config.json is a spec violation. See ADR-013-endpoint-authz-policy-home.md.
  • Accessibility scope: Blind/deaf-user accommodation and broader accessibility design are deliberately out of scope for v6 v1, not omitted by accident; this v1 decision should be revisited in a future accessibility pass.
